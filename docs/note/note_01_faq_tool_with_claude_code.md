# 社内FAQのAIを一人で作って、実際の会社に納めるまで

### Claude Code と過ごした 1 ヶ月の記録と、そのまま持っていけるテンプレート一式

---

ある会社の担当者から、こう相談されたのが始まりでした。

「ヘルプデスクに問い合わせが溜まっていて、毎日同じ質問が来る。若手がそれで消耗している。ChatGPT を使えばいいのは分かるんだけど、社内のデータを外に出すのは無理なんです」

たぶん、同じ話をあちこちで聞いている方がいると思います。私もそのとき、これはこの会社だけの話じゃないなと思いました。

それで作ったのが、社内の文書を根拠に AI が答える FAQ ツールです。作り始めたのが 4 月の頭。実際にその会社のサーバーで動き出したのが、そこから 6 週間後でした。

この記事は、その 6 週間で何を考えて、何を間違えて、Claude Code をどう使ったかの記録です。

---

## 0. この記事に書いてあること

正直に順序立てて書くと、こうなります。

前半は、**何を作ったか**の話です。技術選定でわざと使わなかったもの（データベース、ベクトル DB、形態素解析器、React）と、その理由。それから、このツールで一番時間をかけた「AI に答えさせない仕組み」の話。しきい値の数字も、システムプロンプトの全文も、そのまま載せます。

後半は、**Claude Code をどう使ったか**です。これは精神論ではなく、具体的なファイルと手順の話になります。`CLAUDE.md` に何を書いたか、Skill をいつ作ったか、どういう聞き方をすると出力が変わったか。テストを 120 本から 377 本に増やして、その過程で自分のコードから深刻なバグを 6 件見つけた話も書きます。

最後は、**コードを書き終えてから納品までの 4 週間**の話です。ここが一番きつかった。オンプレのサーバーに入れる作業で詰まった箇所を、13 個すべて書き出しました。

そして記事の後ろに、付録として実物を全部つけています。

- `CLAUDE.md` のテンプレート（注釈つき）
- Skill の定義ファイル 3 本の全文
- 効いた聞き方 12 パターン
- 顧客に渡す事前ヒアリングシート
- コミット前のチェックリスト
- AI が書いた文章を公開する前のチェックリスト
- それらをどこに置けば動くかの説明

コピーして、自分のプロジェクトにそのまま貼れる状態にしてあります。

### 買わないほうがいい方

値段が値段なので、先に書いておきます。

Claude Code をまだ触ったことがなくて、まず使い方を知りたいという方には向きません。公式のドキュメントのほうが正確で早いです。

「AI に丸投げしたら勝手に完成した」という話を期待している方にも向きません。そういう場面は一度もありませんでした。むしろ逆で、任せた結果ひどい目に遭った話のほうが多く出てきます。

Python や Web アプリの基礎がまったくない方も、たぶん途中でつらくなります。コードそのものの解説はしていないので。

### たぶん役に立つ方

Claude Code はもう使っていて、速いんだけど散らかる、という感覚がある方。これは私もずっと感じていて、記事の半分はその対処法です。

個人で作ったものを会社に納めたい方、あるいは納めようとして今まさに詰まっている方。第 10 章の 13 個は、私が実際に踏んだものだけです。

社内 AI や RAG の導入を検討していて、きれいごとではない実費と落とし穴を知りたい方。API の実費は 1 質問あたり何円なのか、35 人規模だと月いくらなのか、全部実数で出します。

## 1. 何を作ったのか

**Inquira** という名前をつけました。社内の文書を取り込んでおくと、社員が日本語で質問したときに、その文書を根拠に AI が答えるツールです。

答えるだけなら ChatGPT でいいわけですが、このツールが必ずやることが 2 つあります。

ひとつは、**どのファイルのどこを根拠にしたかを必ず出す**こと。ファイル名とセクション、それに関連度を表示して、元のファイルをその場で開けるようにしています。

もうひとつは、**根拠が足りないときは答えないで黙る**こと。これが一番難しくて、一番時間をかけた部分です。詳しくは第 4 章に書きます。

機能としては、こんなものが入っています。

PDF・Word・Excel・PowerPoint・CSV・Markdown の取り込み。個人情報のマスキング。社員が自分で解決した内容を共有して全社の資産にする仕組み。よく聞かれる質問を自動でクラスタリングして「これは FAQ にしたほうがいい」と管理者に提示する機能。同じ質問が短時間に繰り返されたときに API を呼ばずに前回の答えを返すキャッシュ。Google アカウントでのログインと、許可したメール・ドメインだけを通す制御。管理者向けの利用状況ダッシュボード。

### いま、リポジトリはこうなっています

数字を出しておきます。全部いま手元のリポジトリから実際に数えたものです。

| | |
|---|---|
| アプリのコード | 6,814 行（14 モジュール） |
| テストのコード | 4,553 行（20 ファイル・関数 377 本） |
| カバレッジ | 88% |
| ドキュメント | 114 ファイル（Markdown 33 / HTML 17 / PDF 16 / 画像 47） |
| 運用スクリプト | 27 本 |
| CHANGELOG | 222 行（v0.1.0 から v0.8.0 まで） |
| 検索速度 | 5,000 チャンクで約 5ms（p95 で 5.4ms） |
| API 実費 | 1 質問あたり 2〜3 円 |

このなかで自分でも意外だったのは、テストが 4,553 行あることでした。実装の 3 分の 2 の量です。

私はもともと、一人で作るときにテストを書くタイプではありませんでした。それが変わったのは、AI にコードを書かせるようになってからです。理由は第 9 章に書きますが、ひとことで言うと、テストの役割が変わったからでした。

## 2. 先に、用語の説明だけ

技術記事が読めなくなる原因の大半は、知っている前提で進むことだと思っています。なので先に用語をまとめておきます。

飛ばしてもらって、分からない言葉が出てきたらここに戻ってきてください。

### AI と検索まわり

**LLM** は ChatGPT や Claude のような、文章を生成する AI の総称です。この記事では Claude を指します。**API** は、自分のプログラムからそういう外部サービスを呼び出す窓口のこと。**トークン**は AI が文章を数える単位で、日本語だとだいたい 1 文字が 1 トークン。料金がこの単位で決まります。

**RAG** は、この記事の中心にある考え方です。AI に社内の情報を覚えさせるのではなく、質問が来るたびに社内文書を検索して、見つかった文章だけを渡して答えさせる。毎回カンニングペーパーを持たせるイメージだと思ってください。

**チャンク**は、文書を検索しやすい大きさに切った断片のこと。このツールでは 1 チャンク 600 文字を上限にしています。就業規則の PDF が 1 つあると、それが数十チャンクになります。

**ハルシネーション**は、AI がもっともらしい嘘をつく現象。「幻覚」と訳されます。第 4 章はほぼ全部この対策の話です。

**システムプロンプト**は、AI に対する「あなたはこう振る舞ってください」という指示書。ユーザーには見えないところで常に効いている前提条件です。**プロンプトキャッシュ**は、毎回同じ指示文を送るときに 2 回目以降を割引にする仕組みで、単価が 10 分の 1 くらいになります。

検索の方式についても触れておきます。**TF-IDF** は古典的なアルゴリズムで、その文書にだけ多く出てくる珍しい単語を重視して探します。AI モデルのダウンロードがいらないので軽い。**文字 N-gram** は、文章を 2〜3 文字ずつ機械的に切って検索する方式です。「有給休暇」なら「有給」「給休」「休暇」。日本語は単語の区切りがないので、この方式だと辞書なしで検索できます。その辞書を使うのが**形態素解析**で、MeCab などのツールと辞書のインストールが必要になります。

**埋め込み**（ベクトル）は、文章を意味を表す数字の列に変換したもの。意味が近ければ数字も近くなるので、言い回しが違っても探せます。ただし変換用の AI モデルが数百 MB 以上必要です。その近さを測る計算が**コサイン類似度**。

**確信度**は、このツールが独自に計算して画面に出している 0〜100% の数字です。AI が自己申告したものではありません。計算式は第 4 章に載せます。

### セキュリティまわり

**PII** は氏名・メール・電話番号のような、個人を特定できる情報のこと。それを `[氏名]` のような伏せ字に置き換えるのが**マスキング**です。

**Luhn（ルーン）アルゴリズム**は、クレジットカード番号が満たす計算上の法則です。この数字列は本当にカード番号なのかを数学的に判定できるので、誤検知を減らせます。

**XSS** は、悪意ある人が画面に JavaScript を仕込んで、他人のブラウザで勝手に実行させる攻撃。そのうち攻撃コードがサーバーに保存されて全員に配信されるタイプを **Stored XSS** と呼びます。第 9 章で自分のコードから見つけたのがこれでした。

**OAuth** は「Google アカウントでログイン」を実現する仕組み。パスワードを自社で預からずに本人確認ができます。**監査ログ**は誰がいつ何を質問したかの記録で、社内ツールではこれがないと導入の許可が下りないことがあります。

### インフラまわり

**オンプレミス**（オンプレ）は、クラウドではなく顧客の自社サーバーに入れて動かす形態のこと。データを外に出せない会社向けです。

**FQDN** は `faq.example.co.jp` のような完全なホスト名。`10.0.0.5` のような IP アドレスとは別物で、ここが第 10 章の詰まりどころにつながります。ホスト名を IP に変換する仕組みが **DNS** で、その対応表の 1 行が **A レコード**。社内 DNS への登録は、たいてい AD 管理者の担当になります。

**リバースプロキシ**は、利用者とアプリの間に立つ中継サーバー。HTTPS 化に使います。Windows Server だと **IIS** という Web サーバーの **ARR** という機能がそれにあたります。これが第 10 章で丸一日溶かした犯人です。

**BOM** は、ファイルの先頭につく「これは UTF-8 です」という 3 バイトの目印。これがないと PowerShell が日本語を Shift-JIS と誤解して文字化けします。**UNC パス**は `\\サーバー名\共有名\フォルダ` 形式の Windows のファイル共有パス。

**SPA** は React や Vue で作る今風の画面のことで、作るには Node.js のビルド環境が要ります。**Docker** はアプリを環境ごと箱詰めして動かす技術。便利ですが、使用を許可していない会社が思ったより多いです。

### 開発まわり

**TDD** は、テストを先に書いて、わざと失敗させてから実装する進め方。**カバレッジ**はテストがコードの何 % を通ったかの割合で、88% なら 12% は一度も実行されていないということです。

**xfail** は「失敗するのを承知で残しているテスト」。直せていない弱点を記録として残すために使います。これは第 9 章で詳しく書きます。

**CI** は、コードを push するたびに自動でテストが走る仕組み。このプロジェクトは GitHub Actions を使っています。**lint**（ruff）はコードの書き方の乱れを自動で見つけるツール。

**SemVer** は `0.8.0` のようなバージョン番号の付け方のルールで、左から MAJOR.MINOR.PATCH。**CHANGELOG** は変更履歴を人間が読む形で残したファイルです。

**CLAUDE.md** は Claude Code が毎回自動で読み込む指示書。プロジェクトのルートに置くだけで効きます。**Skill** は手順書をファイルにしておいて、必要なときだけ読ませる仕組み。この 2 つが記事の中心です。

**プレースホルダ**は `<顧客ドメイン>` のような仮の値。実際の値の代わりに書いておいて、公開しても問題ない状態にすることを指します。

## 3. 何を選んで、何を捨てたか

技術選定の記事はよくありますが、選ばなかったものの理由まで書かれているのは少ないので、そこを厚めに書きます。

先に前提を書いておくと、この構成は技術的にベストを狙ったものではありません。狙ったのは一点だけで、**顧客の社内サーバーに、担当者が 15 分で入れられて、そのあとの運用を人に押しつけない**こと。そこから逆算すると、選択肢はかなり絞られました。

### 全体の流れ

質問が 1 回来たときに何が起きるかを書き出すと、こうなります。

```
   社員（ブラウザ）
    │
    │ 質問を送信
    ▼
 ┌──────────────────────────────────┐
 │  FastAPI（単一プロセス）             │
 │                                   │
 │  1. ログインしている人か確認          │
 │  2. 質問文から個人情報を伏せ字にする   │
 │  3. 社内文書を検索（上位5件）         │
 │  4. 確信度を計算                    │
 │        ↓                          │
 │     低ければ、ここで打ち切る ────────┼──→「該当情報なし」
 │        ↓                          │
 │  5. 直近の同じ質問がないか確認         │
 │  6. Claude API を呼ぶ               │
 │  7. 返答が「分からない」なら表示を揃える │
 │  8. 監査ログに記録                   │
 └──────────────────────────────────┘
    │
    ▼
 data/  ← 全部ファイル。データベースは無し
   ├ faq_master/     取り込み済みナレッジ
   ├ raw/            アップロードされた原本
   ├ audit/          監査ログ
   └ *.json          設定・フィードバック・FAQ候補
```

4 番で打ち切る枝があるのが、このツールの性格を決めています。ここは第 4 章で詳しく書きます。

使っているものは、Web に FastAPI、AI に Anthropic の Claude API、認証に Google OAuth、文書の解析に pypdf や openpyxl といったライブラリ、検索に scikit-learn の TF-IDF。設定は `.env` と管理画面の両方から変えられるようにしています。

Claude を選んだ理由は性能というより、**入力したデータを学習に使わないことが商用契約として明示されている**からです。これが導入の可否を決めます。第 11 章でもう一度触れます。

### 捨てたもの、その 1 — データベース

PostgreSQL も SQLite も使っていません。データは全部 `data/` の下のファイルです。

技術的には DB のほうが優れています。それは分かったうえで捨てました。理由は 3 つあります。

ひとつめは、顧客に DB の運用を要求したくなかったから。インストール手順書に「PostgreSQL のセットアップ」という行が入った瞬間、読む人の心理的なハードルが跳ね上がります。実際、導入の可否は技術の難易度ではなく、担当者が「これならできそう」と思えるかで決まる場面が何度もありました。

ふたつめは、バックアップの説明が一行で済むから。「`data` フォルダを、いま取っているバックアップの対象に足してください」。これで終わりです。`pg_dump` をどう回すかという設計を顧客に負わせずに済みます。

みっつめは、ファイルサーバーの共有フォルダに置けるから。サーバーを入れ替えてもデータが残ります。これは実際に説明したとき、顧客が一番安心した点でした。

もちろん代償はあります。同時に書き込む処理には弱いし、数百人が一斉に使う規模には耐えません。ただ、社内 FAQ の実際の同時アクセスは数人です。将来の理論上のスケールより、今日インストールできることを優先しました。

### 捨てたもの、その 2 — ベクトルデータベース

Pinecone も Chroma も Faiss も使っていません。既定の検索は scikit-learn の TF-IDF です。

理由はひとつで、**オフラインで起動できるようにしたかった**から。ベクトル検索には埋め込みモデルが必要で、初回起動時に数百 MB から 2GB のダウンロードが走ります。社内サーバーが外に自由に出られない環境は珍しくなくて、そこで止まると導入そのものが終わります。

そのうえで、精度が必要な顧客のために切り替えられるようにはしてあります。

```
EMBEDDING_BACKEND=e5-small
```

環境変数を 1 つ変えるだけで multilingual-e5 に切り替わり、初期化に失敗したら TF-IDF に自動で戻ります。「精度は上げたいが、止まるのは困る」という要求は、この形でしか満たせませんでした。

ちなみに実測すると、TF-IDF でも 5,000 チャンクの検索が 5ms 程度で終わります。応答時間の 98% 以上は Claude API との往復なので、検索を速くしても体感は変わりません。ここに凝るのは投資先として間違いです。

### 捨てたもの、その 3 — 形態素解析器

日本語の検索といえば形態素解析、というのが定石です。使っていません。

代わりに文字 N-gram を使っています。

```python
TfidfVectorizer(analyzer="char_wb", ngram_range=(2, 3))
```

理由は導入コストです。MeCab は辞書のインストールが必要で、Windows Server の上で環境を作るのが地味に難しい。文字 N-gram なら分かち書きなしで日本語をそのまま扱えて、追加のインストールがゼロです。

精度は形態素解析に劣ります。それでも、入らない 100 点より入る 80 点を選びました。この判断が正しかったかは、正直まだ分かりません。精度の要求が上がったら考え直すことになると思います。

### 捨てたもの、その 4 — React と、ビルド工程

画面は素の HTML と JavaScript で書いていて、Python 側から文字列として返しています。Node.js が要りません。

これも顧客のサーバーに Node を入れさせないためでした。

ただ、この判断には明確な借金がついています。`app/main.py` が 4,471 行あります。アプリ全体 6,814 行のうち 66% が 1 ファイルです。原因の大半はここで、HTML と JavaScript がそのまま Python のファイルに埋まっているからです。

分割し直すべきだと分かっていて、まだ手をつけていません。第 9 章でもう一度この話をします。

### モジュールの構成

ちなみに、main.py 以外はそれなりに収まっています。

| ファイル | 行数 | 役割 |
|---|---|---|
| `main.py` | 4,471 | ルーティング + 埋め込み HTML/JS（肥大化） |
| `faq_candidates.py` | 458 | 監査ログから FAQ 候補を自動抽出 |
| `ingest.py` | 426 | 文書の解析、チャンク化、PII 検出 |
| `rag.py` | 323 | 検索エンジン。バックエンド切替、学習 |
| `llm.py` | 186 | Claude 呼び出し、システムプロンプト、キャッシュ |
| `masking.py` | 185 | PII マスキング |
| `impact.py` | 163 | 工数削減レポートの集計 |
| `runtime_settings.py` | 162 | 管理画面からの設定変更 |
| `shared_qa.py` | 151 | 社員が共有した Q&A |
| `audit.py` | 73 | 監査ログ |
| `config.py` | 68 | 環境変数の読み込み |
| `auth.py` | 43 | Google OAuth |

分割したモジュールは平均 200 行前後です。つまり、分けようと決めさえすれば適切なサイズになる。それなのに main.py だけが 4,471 行になった。

これは AI の限界ではなくて、私が「どこに書くか」を指示しなかった結果でした。追記するのが一番速いので、放っておくと必ずそうなります。この教訓は第 6 章の `CLAUDE.md` に反映してあります。

## 4. 一番時間をかけたのは、答えさせない仕組みでした

ここが、このプロダクトで書きたかった話の中心です。

### なぜそこにこだわったか

社内 FAQ で最悪の事故は、答えられないことではありません。もっともらしい嘘を、自信ありげに答えることです。

たとえば「有給の申請は 3 営業日前までです」と AI が答えて、実際は 5 営業日前だったとします。それが一度起きると、そのツールは二度と信用されません。社内ツールは信頼を失うと使われなくなり、使われなければ存在していないのと同じです。

だから、精度を上げることより先に、こういう目標を置きました。

答えられないときに、正しく黙れること。

言葉にすると当たり前ですが、実装するとこれが一番難しかった。

### 防御を三段にした

一箇所の工夫ではなく、独立した三段にしました。ひとつ破られても次で止まるようにするためです。

**一段目は、検索スコアが低ければ AI を呼ばないこと。**

一番確実なハルシネーション対策は、AI に喋らせないことです。

```python
# 確信度: top-1 スコアがこの値未満ならLLM呼び出しを行わず「該当情報なし」を返す
# TF-IDF char_wb の経験値: 関連質問は 0.15+, ノイズマッチは 0.05-0.07 程度
min_score_threshold: float = 0.08
```

コメントに書いてある数字は、実際のデータで観測した値です。関連する質問なら 0.15 以上に、無関係なノイズなら 0.05〜0.07 くらいに落ち着く。その間の 0.08 を境界にしました。

この 1 行は精度とコストの両方に効きます。呼ばなければ課金もされないので。

そのうえで、ノイズが 1 件だけ強く当たったケースを別に弾いています。

```python
# 突出ノイズ判定: top1 が弱く（< 0.12）2位との差が極端な場合のみ
# 0.12 以上は正解1件にヒットしている可能性が高いので回答に進める
if top < 0.12 and len(scored_chunks) >= 2:
    second = scored_chunks[1][1]
    if second / top < 0.3:
        return 0
```

1 位だけ妙に高くて 2 位以下が全滅している状態は、関連文書が本当にあるのではなく、たまたま文字列が一致しただけであることが多い。これはログを眺めていて気づいたパターンでした。

**二段目は、システムプロンプトで推測の語彙を名指しで禁止すること。**

ここは何度も書き直しました。最終形の中心はこれです。

```
ルール（厳守）:
1. 提供された [参考情報] に**明示的に書かれている内容のみ**を根拠に回答する
2. [参考情報] に直接の答えが書かれていない場合は、推測せず以下の文言を返す:
   「該当情報が見つかりませんでした。社内ヘルプデスクにお問い合わせください。」
3. 推測表現の使用を禁止: 「だと思います」「おそらく」「一般的には」「〜のはずです」
   「もしかすると」「推察します」など、不確実な語彙は一切使わない
4. 一般常識・あなたの事前知識からの補完を禁止する
   （例: マニュアルに書かれていない手順を「業界の慣習」で埋めない）
5. 回答末尾に出典（ドキュメント名やID）を必ず明記する
```

効いたのは 3 番でした。「推測しないでください」という抽象的な指示より、禁止したい言葉を並べたほうが圧倒的に守られます。

これは後で気づいたのですが、Claude Code に対する `CLAUDE.md` の書き方とまったく同じ原理でした。抽象的な理想より、具体的な禁止のほうが効く。

4 番も実戦で必要になったものです。AI は親切なので、マニュアルに書いていない手順を「一般的にはこうです」で埋めようとします。社内規程の話において、一般論は間違いと同義です。

**三段目は、返ってきた答えをもう一度検査すること。**

プロンプトで指示しても、破られる可能性はゼロにはなりません。なので出力側でも見ます。

```python
# LLM が「答えられない」と判断したフレーズ。検出時は sources / confidence を 0 に揃える
_NO_ANSWER_MARKERS = (
    "該当情報が見つかりませんでした",
    "関連する情報も見つかりませんでした",
)
```

なぜこれが要るのか。「該当情報が見つかりませんでした」と答えているのに、画面には確信度 72%、参照ドキュメント 3 件、と出ている状態が起きうるからです。

機能としては全部正しく動いています。でもユーザーから見たら、完全に壊れて見える。

画面に出る信号を全部、意味として揃える。地味ですが、信頼されるかどうかを一番左右したのはここでした。

### 「答える」と「答えない」の二択をやめた

最初は 2 状態でした。運用してみて、これが現実に合っていないと気づきました。

直接の答えは書かれていないけれど、明らかに関連する記述はある。このケースが思ったより多いんです。それを「該当情報なし」で切り捨てると、目の前にある有用な情報を捨てることになります。

そこで 3 つめの状態を作りました。

```python
is_reference = confidence < 50
```

確信度が 50% を切ったときは、専用の別プロンプトに切り替えます。そこでは「以下は関連しそうな情報です」と、公式の回答ではないことを最初に明示させる。引用と要約に留めさせて、推測は引き続き全面的に禁止。そして画面の上に `⚠ 公式FAQ未登録の参考情報です（正確性は保証されません）` を必ず付けます。

自信の度合いに応じて話し方を変える、ということをやっています。人間の担当者も「規程にはこう書いてあります」と「たしか関連する話が別の資料にあった気がします」を区別して喋るので、それを実装しただけとも言えます。

### 確信度に、それらしい数字を出さない

画面に数字を出す以上、根拠がないとまずい。演出で数字を出すのが一番よくないと思っています。

```python
base = min(95, int(30 + top * 250))
relevant = sum(1 for _, s in scored_chunks if s >= settings.min_score_threshold)
return min(98, base + max(0, relevant - 1) * 3)
```

検索スコアから線形に出して、関連文書が複数あれば少し足す。1 件だけより裏が取れているので。

上限を 95 と 98 で止めているのは意図的です。100% は絶対に出しません。AI の回答に確信度 100% と表示されたら、それは嘘だからです。

ユーザーに「必ず出典を確認する」という習慣を残しておきたくて、上を開けたままにしています。

### マスキングの本当の敵は、見落としではなく誤検知でした

送信前に個人情報を伏せ字にする機能です。開発時間の大半は、見落としをなくすことではなく、誤検知を減らすことに消えました。

きっかけはこれです。

```
2024-06-24 084412  →  [カード番号]
```

タイムスタンプがクレジットカード番号として検出されました。業務ログを取り込むと、これが大量に出ます。

マスキングが過剰にかかると、検索に必要な情報まで潰れて回答できなくなる。見落としと同じかそれ以上に厄介です。

対策は 2 段構えにしました。

```python
def _is_likely_credit_card(s: str) -> bool:
    """Luhn + 数字グループ構造で誤検知を抑える厳密判定。

    除外する代表パターン:
      - タイムスタンプ 「2024-06-24 084412」（グループサイズ 4-2-2-6）
      - 4桁未満や8桁超の塊が混ざるもの
    カード番号の典型構造（4-4-4-4, 4-6-5, 16桁連続 等）のみ True。
    """
```

Luhn アルゴリズムでチェックディジットを検証したうえで、数字のグループ構造も見る。4-4-4-4 のような区切り方をしているか。

そして、モジュールの先頭にこう書きました。

```python
実装ポリシー:
- 完全な PII 除去は保証しない（深層モデル必須レベル）。
  "見落とし時の被害を減らす"目的の防御層
```

できないことを、コードに書いて宣言する。

「個人情報を完全に除去します」と顧客に説明したら、それは嘘になります。防御の 1 枚でしかないと正確に伝えたほうが、長い目で見れば信用されると思っています。

### 動くことと、運用できることは別だった

これは設計というより、思い知らされた話です。

埋め込みキャッシュの最初の実装は、コーパス全体で 1 つのハッシュキーを作っていました。機能としては完璧に動きます。

ただ、1 ファイル追加するたびに全件の再計算が走って、30 分から 2 時間かかりました。

```python
"""チャンク単位の差分キャッシュ。

旧実装は全チャンクで1つのハッシュキーを作っていたため、1ファイル追加
するだけで全件再エンコードが発生していた（200K chunks で 30分〜2h）。
本実装は (chunk_id, text_hash) → vector をキャッシュし、追加/変更され
たチャンクだけを再計算する。
"""
```

キーの単位を変えただけで、1 ファイルの追加が数秒になりました。

機能としては最初から動いていたのに、運用としては破綻していた。「動くか」の次に「毎週これをやれるか」を聞くようになったのは、この件からです。

### 学習機能に、上限をかけた

👍👎 のフィードバックを検索スコアに反映していますが、影響の上限を ±15% で止めています。

```python
def _boost_factor(source: str, fb) -> float:
    """フィードバックに基づくブースト係数。
    ネット票数 (up - down) を tanh で滑らかにし、最大 ±15% の倍率に。
    例: net=+5 → ×1.114 / net=-5 → ×0.886 / net=0 → ×1.0
    """
```

`tanh` を使っているのは、票が積み上がっても効果が飽和するようにするためです。

無制限に学習させると、声の大きい少数の投票で検索結果が支配されます。社内ツールだと、それは「特定の部署の資料ばかり出てくる」という形で表面化します。

学習は、暴走しない上限とセットにして初めて機能する。これは実際に暴走させてみるまで、頭では分かっていても実感がありませんでした。

### 売るために要った機能の話

技術的には地味なんですが、商談で一番効いた機能なので書いておきます。

```python
# 1質問あたりの「資料を探す or 人に聞く」想定削減時間（分）
minutes_saved_per_answered_query: int = 8
# 共有回答1件あたりの整備時間削減（分）
minutes_saved_per_faq_shared: int = 20
# 平均時給（円）。削減コスト換算用
hourly_rate_yen: int = 3500
```

監査ログから何件答えたかを集計して、削減できた時間と金額に換算して管理画面に出します。しかも、この前提の数字は管理者が変えられるようにしました。

なぜこれが重要かというと、導入を決めた担当者は、社内でその成果を説明しないといけないからです。

「便利です」では稟議は通りません。「月に 120 時間、42 万円ぶん減りました」なら通ります。

継続を決めるのは、使っている社員ではなく予算を持っている人です。その人に渡す数字を、ツール自身が作る。個人で作ったものを会社に売るなら、この視点は機能開発と同じ優先度で持っておいたほうがいいと思います。

## 6. CLAUDE.md — 置くだけのファイルが、一番効きました

### これは何を書く場所なのか

`CLAUDE.md` は、プロジェクトのルートに置いておくと、Claude Code が毎回のセッションの最初に自動で読む指示書です。

私は最初、これをプロジェクトの概要を書く場所だと思っていました。それで概要を書いてみたのですが、効果がほとんどありませんでした。当たり前で、概要ならコードを読めば分かるからです。

効いたのは、放っておくと必ず間違えることを、先回りして禁止する記述でした。

つまりこれは、**過去に起きた事故の再発防止書**です。

運用ルールはシンプルにしています。同じミスを 2 回説明したら、`CLAUDE.md` に書く。3 回目を説明したことは、それ以来ありません。

### 実際に起きた事故から

私の `CLAUDE.md` に書いてあるルールは、全部実際の事故から生まれています。3 つ紹介します。

#### PDF が中国語のフォントで出てきた件

顧客に配る操作マニュアルを WeasyPrint で PDF にしたら、漢字が中国語の書体で出力されました。

「直」「経」「値」あたりの字形が明らかに違う。日本の会社に出す資料としては、それだけで終わりです。

原因は、Linux で日本語フォントが指定されていないと、フォントを選ぶ仕組みが CJK 共通のフォントから中国語圏のものを優先してしまうこと。

一番怖かったのは、**Mac の開発機では正常に見える**ことでした。気づかずに顧客へ渡す事故が起きうる。実際、生成した本人が気づかなければそのまま出ていました。

なので毎回指示するのではなく、ルールにしました。

```markdown
### 日本語フォント (中華フォントへのフォールバック防止)

PDF 化される HTML には、必ず以下の font-family を使用すること。
weasyprint で生成する PDF が中国語フォントにフォールバックする事故を防ぐため、
IPA フォントを明示的に末尾に含める。

​```css
font-family:
  "Hiragino Kaku Gothic ProN",
  "Hiragino Sans",
  "Yu Gothic",
  YuGothic,
  Meiryo,
  "IPAPGothic",
  "IPAGothic",
  sans-serif;
​```

- Mac → Hiragino 系が優先される
- Windows → Yu Gothic / Meiryo が優先される
- Linux (weasyprint) → IPAPGothic / IPAGothic が使用される
  (これを書かないと weasyprint が CJK フォントから中国語フォントを選ぶ事故が起きる)
```

書いていて気づいたのは、なぜそうするのかを併記すると効きが違うということでした。理由があると、似たような別の状況にもルールを応用してくれます。理由なしの命令は、想定していなかったケースであっさり破られます。

#### 顧客の実データを、あやうくコミットするところだった件

オンプレの作業中、手順書に顧客の社内ドメイン、社内 IP、ファイルサーバーの共有パス、SSL 証明書の Thumbprint がそのまま書かれた状態で、コミットの寸前まで行きました。

これは AI のせいではありません。私が会話でその値を渡して、AI が親切に手順書へ埋め込んだだけです。渡した情報は成果物に出る、という当たり前の帰結でした。

なので対策は AI 側ではなく、運用側に置くしかない。

```markdown
### 顧客固有情報の取扱

- 顧客名、社内ドメイン、社内 IP、UNC パス、SSL 証明書 Thumbprint 等は **絶対にコミットしない**
- 例示する場合は `<CUSTOMER_DOMAIN>`, `example.local`, `10.0.0.x`,
  `\\fileserver\share\inquira` のような一般的な値を使用
- 実値は `.private/` 配下で管理 (.gitignore 済み)
- コミット前に下記のチェックを実行することを推奨:
  ​```bash
  git diff --cached | grep -iE '<顧客固有語>|192\.168\.|@gmail\.com|sk-ant-|GOCSPX-'
  ​```
```

grep のパターンに `sk-ant-`（API キー）と `GOCSPX-`（Google の OAuth シークレット）を入れているのが実務上のキモです。開発中に一番漏れやすいのがこの 2 つでした。

#### 資料の文体が、押しつけがましくなっていた件

AI に顧客向けのマニュアルを書かせると、善意で余計なことを書きます。

「ご不明な点は社内の情報システム部門へお問い合わせください」

一見親切です。でもこれは、顧客の組織構造を勝手に決めつけている文章です。情シス部門がない会社、外部に委託している会社では、この一行が信頼を削ります。

```markdown
### 「情シス」「弊社」「A 社」等の表現

- 「不明点は社内情シスへ」のような **押しつけがましい表現は使わない**
  (顧客側の組織構造を勝手に決めつけることになる)
- 「弊社」「A 社」のような **特定の組織を指す表現は使わない**
  (汎用テンプレートとして使えなくなる)
- 推奨表現: 「サービス提供元」「本ツールを導入された管理者の方」「サービスご利用元」
```

このルールは、思っていた以上の副産物を生みました。

特定の顧客向けに作った資料が、そのまま次の会社に出せるテンプレートになったんです。1 社目の納品物が資産になるか使い捨てになるかは、この文体ルールで決まっていました。

### 書くと効くもの、書いても効かないもの

1 ヶ月やってみて、効いたのは 6 種類くらいでした。

事故の再発防止。環境に固有の罠（PowerShell は BOM 付きで保存する、など）。文体の禁止事項。バージョン番号を 2 箇所同期させるといった、AI が最も忘れやすい機械的な作業。CHANGELOG に必ず書くという記録の義務。それとブランチ名やタグの命名規約。

逆に、書いても薄かったものもあります。

プロジェクトの機能説明を延々書くのは、コードを読めば分かることなので無駄でした。しかも肝心の禁止事項が埋もれます。「丁寧に書いて」「良いコードを書いて」も、判定基準がないので何も変わりません。

分量にも限界があります。500 行を超えたあたりから、重要度が均されて守られなくなりました。**200 行以内が実用の上限**だと思います。私の実物は 100 行くらいです。

あと、一度書いて放置すると陳腐化します。事故が起きるたびに追記して初めて機能する、育てるファイルです。

完全なテンプレートは付録 A に載せました。私が踏んだ地雷が全部入っています。

## 7. Skill — 3 回説明したら、ファイルにする

### CLAUDE.md との使い分け

Skill は、手順書をファイルにしておいて、必要なときだけ読ませる仕組みです。

`CLAUDE.md` が常時読まれる憲法だとすると、Skill は必要なときに開く業務マニュアルにあたります。

作るかどうかの基準は 1 つにしています。同じ手順を 3 回説明したら Skill にする。

`CLAUDE.md` が 2 回で Skill が 3 回なのは、分量の違いです。1〜2 行で済む禁止事項は `CLAUDE.md` に。数十行の手順は Skill に。`CLAUDE.md` に長い手順を書くと、常時読み込みでトークンを食って、他のルールを薄めてしまいます。

### 実際に作った 3 本

全文は付録 B にあります。ここでは、なぜ必要になったかだけ書きます。

**`ja-pdf-export`** は日本語 PDF の生成用です。前に書いたフォント事故があって、フォント指定を `CLAUDE.md` に書いたのですが、それだけでは足りませんでした。

実際には毎回、フォント指定を確認して、生成後に目視で中国語になっていないか見て、A4 に収まっているか確認して、表の途中で改ページされていないかを見る必要がありました。4 ステップです。`CLAUDE.md` に書くには長すぎる。Skill が正解でした。

**`release-guard`** はリリース前の確認用です。一人で開発していると、リリース作業が一番雑になります。

私が何度もやらかしたのは 3 つ。`pyproject.toml` のバージョンは上げたのに `app/__init__.py` の `__version__` を上げ忘れる。CHANGELOG に書き忘れる。`.env` の値をコミットしそうになる。

全部、機械的にチェックできることでした。なので丸ごと Skill にして投げました。いまは「リリースして」の一言で、バージョンの同期、CHANGELOG の昇格、秘密情報の grep、テストの実行まで走ります。

**`customer-handoff`** は顧客に渡す資料の生成用です。金額的なインパクトが一番大きかったのはこれでした。

会社に納品するとき、必要なドキュメントは 1 種類ではありません。

顧客の IT 部門にはインストール手順書。AD や DNS の管理者には設定依頼書。インフラ担当にはリバースプロキシの設定依頼書。顧客側の管理者には管理画面のクイックスタート。そして全社員には、専門用語を 1 つも使わない 1 枚の利用ガイド。

同じ製品なのに、5 種類の違う読者に向けて、違う文体と粒度で書く必要がある。しかも AD 管理者は製品のことを何も知らないので、製品の説明を 2 行以内に留めて依頼内容だけを表にする、といった書き分けが要ります。

手作業でやると 1 社あたり数日かかります。Skill にすれば、顧客ごとの差分を入れるだけになりました。

リポジトリに PDF が 16 個ある理由がこれです。AI 開発の本当のレバレッジは、コードよりも納品ドキュメントのほうにあったというのが、正直な実感です。

## 8. 出力が変わった聞き方、12 パターン

ここは一番すぐに試せる部分だと思います。毎日 1 ヶ月以上使い続けて、明らかに出力の質が変わった聞き方を 12 個に絞りました。

コピー用の全文は付録 C にあります。

### 1. エラーは、そのまま貼る

整形も要約もしないで、ターミナルの出力をそのまま全部貼る。

エラーログには、自分が「関係ないな」と判断した情報が詰まっています。実行したディレクトリ、Python のパス、ライブラリのバージョン、スタックトレースの深さ。要約するというのは、診断に必要な情報を捨てる行為でした。

実例をひとつ。Cloudflare のツールを起動しようとしたら `Illegal instruction: 4` で落ちたことがありました。この文字列を丸ごと貼ったら、Apple Silicon の Mac に Intel 用のバイナリが入っている、というところまで一発で特定されました。

「起動できません」と要約していたら、何往復もしていたはずです。

### 2. コピペで動く形で、と明示する

「起動方法を教えて」ではなく、「そのままターミナルに貼って動く 1 行で。ディレクトリ移動も含めて」と頼む。

AI は放っておくと説明を返します。「プロジェクトディレクトリに移動して、仮想環境を有効化して……」という文章は、読んで自分の環境に翻訳する手間を発生させます。

```bash
cd ~/faq_platform && PYTHON=python3.11 ./scripts/serve.sh
```

こう返してもらうほうが速い。毎回言うのが面倒になったので、これは `CLAUDE.md` に書いて恒久化しました。

### 3. 出力の形式を指定する

「導入手順をまとめて」ではなく、「顧客の IT 部門にそのまま渡せる HTML で。チェックボックス付き、フェーズごとに色分け、所要時間を明記」と頼む。

これは私のなかで一番過小評価していたテクニックでした。

Claude Code はテキストだけでなく、構造化された資料を作れます。色分けされたチェックリスト、フェーズマップ、大きな数字での統計表示、タイムライン。

そして重要なのは、その成果物が自分用のメモと顧客への配布資料の両方になることです。リポジトリの HTML 17 本と PDF 16 本は、ほぼ全部この頼み方から生まれました。

個人で作ったものを会社に売り込むとき、資料の見た目は技術力と同じくらい効きます。ここを AI にやらせない手はありません。

### 4. 進捗の棚卸しを頼む

「これまでのやり取りと git 履歴から、残タスクを優先度順に整理して」

AI は git log、CHANGELOG、会話履歴、ファイルの状態を同時に見られます。人間より正確に棚卸しできる、数少ない領域だと思っています。

一人で開発していて一番怖いのは、何をやり残したか分からなくなることです。週に 1 回これをやるだけで、止まりにくくなりました。

### 5. フェーズを分けて、途中で止めさせる

「認証機能を作って」ではなく、「まず 3〜5 フェーズに分割した計画だけ出して。実装はまだしないで」と頼む。

AI は一気に大量の変更を入れられます。それが問題で、5 ファイルを同時に変えられてから動かなくなると、どの変更が原因か切り分けられなくなります。

速いから任せるのではなく、速いから細かく切る。逆説的ですが、こっちのほうが結果的に速い。

### 6. スクリーンショットを送る

Google Cloud Console、Cloudflare、IIS、Windows のダイアログ。この手の画面は文章で説明しきれないし、しかも頻繁に変わります。

「同意画面の設定はどこですか」と 3 往復するより、スクリーンショット 1 枚のほうが速い。オンプレの作業中は、この差が数時間になりました。

### 7. コミット前に、必ず一度聞く

「これ、push して大丈夫？ `.gitignore` も見て、含まれちゃいけない情報がないか確認して」

AI は `.gitignore` の中身、ステージング中の差分、ファイルの中身を全部読んだうえで判断できます。

これは、チェックリストを自分の記憶に頼らないという話です。顧客情報を混入させかけた件以降、機械的にやるようにしました。

### 8. 失敗するテストを先に書かせる

「マスキング機能を作って」ではなく、「マスキング機能の仕様を満たすテストを先に書いて。失敗することを確認してから実装して」

これが品質の生命線です。詳しくは次の章に書きます。

### 9. 批判させる

「この設計でいい？」と聞くと、たいてい「いいですね」と返ってきます。AI は既定では同意的です。

「この設計の欠点を 3 つ挙げて。特に、規模が 10 倍になったときに壊れる箇所」と聞くと、返ってくるものが変わります。

これで得た指摘のひとつが、「TF-IDF は 1 ファイルの語彙が巨大だと IDF が希薄化して、他の文書が検索から落ちる」というものでした。

そして実際に、20 万チャンクのチャットログを取り込んだ瞬間にそれが現実化しました。事前に言われていたので、対処を即断できました。

### 10. 記録から資料を作らせる

「CHANGELOG と git log から、今週の成果を顧客報告用にまとめて」

これをやるようになってから、CHANGELOG を書く動機が変わりました。後で AI が使えるから書く。記録のコストが投資に変わった感じです。

### 11. 数字を測らせる

「パフォーマンスを改善して」ではなく、「5,000 チャンクでの検索時間を実測するベンチマークを書いて。改善前後で比較できる形で」

顧客に「速いです」は通用しません。「5,000 文書で 5ms です」なら通用します。そしてその数字は、自分が測らない限り存在しません。

AI はベンチマークのスクリプトを書くのが得意です。測定を頼むことが、そのまま営業資料を作ることになっていました。

### 12. 公開資料であることを宣言する

「これは社外に公開する資料です。個人名・顧客名・内部 IP を一切含めないこと」

私は実際に、AI が生成したレポートに自分の本名がそのまま入っていたことがあります。会話の文脈から親しみを込めて書いてくれたわけですが、公開資料としてはアウトでした。

AI は、その文章がどこまで公開されるかを知りません。それは指示する側の責任です。

### 使い分け

バグが出たら 1 番から 5 番へ。新機能を作るなら 8 番、9 番、5 番の順。顧客に資料を出すなら 3 番と 12 番、そのあと人間のレビュー。進捗が分からなくなったら 4 番と 10 番。性能を主張したいなら 11 番。コミット前は 7 番。

## 9. テストを 120 本から 377 本にした 2 時間

### AI 開発で、テストの役割が変わった

普通の開発において、テストは品質保証の手段です。

AI に書かせるようになってから、意味が変わりました。

AI は、依頼していない箇所も「ついでに」改善します。善意で。その結果、別の場所が壊れる。しかもこちらは、その変更に気づいていない。

つまり AI 開発でのテストは、自分が見ていない場所で何かが壊れたことを知るための警報装置です。

目的が変わると、書くべきものも変わります。カバレッジの数字より、壊れたら致命的な箇所を全部押さえているかのほうが重要になりました。

### やった手順

2 時間で、テストを 120 本から 293 本に増やして（現在は 377 本）、実装のバグを 6 件見つけました。手順はこうです。

**まず、攻撃者の視点でテストを書かせます。実装は見せません。**

```
tests/test_security.py を作って。
このアプリに対する攻撃を想定したテストを書いて:
- XSS（管理画面から保存した値が HTML に反映される箇所すべて）
- SQL/コマンドインジェクション
- 認証バイパス（未ログインで管理 API を叩く）
- パストラバーサル（../ を含むファイル名でアップロード）

重要: 「今の実装が通るテスト」ではなく、
「安全なアプリなら通るはずのテスト」を書いて。
落ちてもいい。
```

最後の 3 行が決定的でした。

これを書かないと、AI は現在の実装に合わせたテストを書きます。それは何も検出しません。全部通って、安心して、終わり。

**次に、落ちたテストの側が正しいと仮定して直します。**

このとき見つかったバグをひとつ紹介します。

管理画面から設定できる「組織名」が、HTML にエスケープなしで埋め込まれていました。

```
再現手順:
1. PUT /api/admin/settings に {"org_name": "<script>alert(1)</script>"} を送信
2. GET / でメインページを取得
3. <p> タグ内に <script>alert(1)</script> が未エスケープで埋め込まれる

影響: 管理画面に値を保存できる者が、全社員のブラウザで任意 JS を実行できる
```

Stored XSS です。社内ツールだから安全、という油断が生む典型でした。

修正自体は単純でした。

```python
def _esc(s: str | None) -> str:
    """HTML エスケープ（XSS 防止）。組織名等を HTML に埋め込む前に必ず通す。"""
    return html.escape(str(s or ""), quote=True)
```

ただ、重要なのは修正の中身より、このバグを AI が自分で書いたコードの中から見つけたという事実のほうです。

書き手としての AI と、テスターとしての AI は、別人格として使えます。同じセッションでも、視点を指定すれば切り替わる。

**そして、直せないものは記録として残します。**

全部直す必要はありませんでした。私は 3 件を `xfail`、つまり失敗を承知のテストとして残しています。

これが実務上けっこう大事で、直せていない弱点がテストとして明示されている状態は、弱点があることを誰も知らない状態より、はるかに安全です。

引き継ぎのときにも効きます。「ここは弱い」がコードに書いてある。

### 結果

テストは 120 本から 293 本。カバレッジは 84% から 88%。`app/auth.py` は 59% から 89%、`app/runtime_settings.py` は 62% から 100% になりました。見つかったバグは 6 件で、全部直しました。

かかった時間は 2 時間です。

### そのうえで、正直に書いておくこと

信用してもらうために、都合の悪い数字も出します。

`app/main.py` は 4,471 行あります。アプリ全体の 66% が 1 ファイルに集中しています。明確な技術的負債です。

原因ははっきりしていて、AI は今あるファイルに追記するのが一番速く、私がそれを止めなかったからです。機能を足すたびに main.py が膨らんで、気づいたら 4,471 行になっていました。

AI 開発では、どこに書くかを人間が決めないと、必ず 1 ファイルに集中します。「新しい機能は新しいモジュールに」というルールを、最初から `CLAUDE.md` に書いておくべきでした。

付録 A のテンプレートには反映してあります。同じことを繰り返さないでください。

## 10. コードが書き終わってから、動き出すまでの 4 週間

ここが、個人で作ったものを会社に納めるときに、一番詰まるところです。

私の体感で言うと、機能の実装に 2 週間、実際にその会社で動くまでにさらに 4 週間かかりました。

後半の 4 週間に、コードを書く作業はほとんどありません。そしてこの 4 週間の存在を知らないと、見積もりが 3 倍外れます。

### 詰まった 13 箇所、全部

発生した順に書きます。そのままチェックリストとして使えると思います。

| # | 何が起きたか | 原因 | どうすべきだったか |
|---|---|---|---|
| 1 | Docker 前提で進めていたら、途中で Docker 不可と判明 | 環境の確認不足 | キックオフ前に「Docker 使えますか」と聞く |
| 2 | Windows Server に Linux 用の `install.sh` を渡そうとした | OS の確認不足 | 最初に OS を聞く |
| 3 | 管理者権限がなく、タスクスケジューラに登録できなかった | 権限の確認不足 | 「サーバーの管理者権限ありますか」と聞く |
| 4 | `install.ps1` が文字化けしてパースエラー | BOM なし UTF-8 を PowerShell が Shift-JIS と解釈した | スクリプトは BOM 付き UTF-8 で配布する |
| 5 | CMD と PowerShell の構文を顧客が混同した | 案内が曖昧だった | コマンドに必ず「PowerShell で」と明記する |
| 6 | Google OAuth が IP アドレスのリダイレクト URI を拒否した | Google の仕様 | 「社内 DNS で FQDN を割り当てられますか」と聞く |
| 7 | OAuth のテストユーザー登録を忘れて、全員ログインできなかった | 手順書から漏れていた | 提供側の準備リストに必ず入れる |
| 8 | DNS の設定権限がなかった（担当者と AD 管理者が別人） | 権限分離の見落とし | 「DNS は誰が触れますか」と聞く |
| 9 | リポジトリに顧客固有の値を書いてしまった | こちらのミス | プレースホルダ運用とコミット前 grep |
| 10 | Mac から Windows サーバーへ ZIP を直接渡せなかった | 転送経路の確認不足 | 最初から GitHub 経由のダウンロードを案内する |
| 11 | ダウンロードで BOM が剥がれて文字化けした | PowerShell 5.1 の `Invoke-WebRequest` の挙動 | `WebClient.DownloadFile` を使う |
| 12 | DNS の A レコードを AD サーバー自身の IP で登録して繋がらなくなった | アプリサーバーと DNS サーバーが別マシンであることの見落とし | 登録後に必ず `nslookup` で検証する |

13 番で丸一日溶かしました。

リバースプロキシが OAuth のリダイレクト先ホスト名を勝手に書き換える。症状は「自分のサイトで 404」なので、そこから「プロキシのヘッダ書き換え設定」に到達するのが本当に難しい。

この 13 個のうち、AI に聞いて即解決したのは 4 番、11 番、13 番の 3 つだけでした。

残りの 10 個は、顧客に何を聞いておくべきだったかという話です。技術の失敗ではなく、段取りの失敗でした。

### だからヒアリングシートを作りました

上の 10 個は、キックオフの前に 6 つのことを埋めてもらうだけで全部消えます。

サーバーの環境（OS、Docker の可否、Python、管理者権限、外向きの通信）。ネットワークと DNS（社内ドメイン、DNS の設定権限、希望するホスト名）。データの保存先（サーバー内か共有か、バックアップ運用）。アクセス制御（管理者のアカウント、全社に開放するか、会社のドメイン）。HTTPS 化（リバースプロキシの有無、証明書、担当部署）。そして役割分担（誰が何を何分でやるか）。

記入式の完全版は付録 D にあります。

これは私が 13 回詰まって作ったものです。1 社目から使ってください。

### 顧客に説明するときの判断表

会話でそのまま使える表も置いておきます。

公開する URL の形式について。

| 形式 | Google OAuth | 全社員から見える | 用途 |
|---|---|---|---|
| `http://localhost:8000/` | 通る | サーバー上だけ | デモ |
| `http://10.0.0.5:8000/` | **通らない** | 社内 LAN | 使えない |
| `http://inquira.example.jp:8000/` | 通る | 見える | 本番（HTTP） |
| `https://inquira.example.jp/` | 通る | 見える | 本番（推奨） |

データの保存先について。サーバー内に置くと、入れ替えのときに消えます。ファイルサーバーの共有に置けば、既存のバックアップ体制にそのまま乗ります。本番は共有一択でした。

## 11. 実費と、商談で効いたこと

「AI で作ると安い」と言うだけでは提案になりません。実数を出します。

### API の実費

Anthropic の API は完全な従量課金です。月額の固定費はありません。最低使用料もありません。使わなかった月は 0 円です。

1 質問あたりのコストは、こうなります。

| 構成 | 入力 | 出力 | コスト |
|---|---|---|---|
| チャンク 5 件 × 300 字 | 約 2,500 トークン | 約 200 トークン | 約 1.7 円 |
| チャンク 5 件 × 800 字 | 約 5,000 トークン | 約 300 トークン | 約 3.1 円 |
| 参考情報 10 件 + 長文 | 約 12,000 トークン | 約 500 トークン | 約 6.8 円 |

このツールの実装値、チャンク 350 字を 5 件と出典で、1 質問あたり 2〜3 円です。

規模別の月額に直すとこうなります。

| 規模 | 月間の質問数 | 月額 |
|---|---|---|
| 5〜10 名 | 330〜1,760 問 | 660 〜 5,500 円 |
| 35 名（控えめ） | 3,850 問 | 7,700 〜 12,000 円 |
| 35 名（標準） | 7,700 問 | 15,000 〜 25,000 円 |

削減のために 2 つ実装しています。プロンプトキャッシュで共通の指示部分を割引価格にするのと、同じ質問が短時間に繰り返されたときに API を呼ばない回答キャッシュ。後者で 30〜50% 減ります。

小さい組織ほど同じ質問の繰り返し率が高いので、回答キャッシュは規模が小さいほど効きます。提案のときに刺さるポイントです。

技術以外で、一番効いた事実を書いておきます。

「Anthropic の API は、入力したデータをモデルの学習に使いません。商用契約として明示されています」

社内 AI の導入が止まっている理由は、ほぼこれです。便利なのは分かっているが、うちのデータが学習されるのは無理だ、という壁。

商用 API を使う設計にするだけで、この壁は越えられます。そして多くの担当者は、この事実を知りません。

提案の最初の 1 分でここを伝えるかどうかで、会話の方向が変わりました。

最初は「え？」という反応でした。でも説明すると、ハードルが下がったと感謝されました。

### AI が作ったブランチを、そのまま使い続けた

### とにかく全部取り込んだ

RAG の精度は、モデルではなく入力データの質で決まります。

テストで自分のブログのエクスポート（9MB）を取り込んだ瞬間、回答の品質が崩壊しました。該当の記事はちゃんと検索でヒットしているのに、確信度が 0% になる。

データは多いほど良い、というのは RAG では明確に間違いです。

# 顧客引き渡しドキュメント生成

## 原則

**同じ製品でも、読者ごとに別のドキュメントを作る。** 1 つの資料を全員に渡すと、
IT 部門には冗長で、一般社員には難解、という最悪の結果になる。

## 生成する 5 種類

| # | 読者 | ドキュメント | 前提知識 | 分量の目安 |
|---|---|---|---|---|
| 1 | 顧客 IT 部門 | インストール手順書 | 高い | 詳細に。コマンドは全てコピペ可能な形で |
| 2 | DNS / AD 管理者 | DNS 設定依頼書 | 高いが**別担当者** | 1〜2 ページ。依頼内容だけ |
| 3 | インフラ担当 | リバースプロキシ設定依頼書 | 高い | 1〜2 ページ。設定値を表で |
| 4 | 顧客側の管理者 | 管理画面クイックスタート | 中 | 画面ごとに何ができるか |
| 5 | 全社員 | 利用ガイド | **ゼロ** | **1 ページ**。図中心、専門用語ゼロ |

## 書き分けのルール

### 依頼書（#2, #3）で必ず守ること

- **依頼相手は製品を知らない**前提で書く。製品の説明は 2 行以内に留める
- 「何を設定してほしいか」を**表**で示す（文章にしない）
- 設定後の**検証コマンド**を必ず含める（例: `nslookup <hostname>`）
- 想定所要時間を明記する（相手が着手判断できる）

### 全社員向け（#5）で必ず守ること

- **専門用語を 1 つも使わない**（「RAG」「LLM」「OAuth」全て禁止）
- 1 ページに収める。読まれない資料は存在しないのと同じ
- 「ログインできないとき」の対処を必ず含める（問い合わせが最も多い）

## 付録 G：テンプレートの設置方法 — どこに、どうやって置くのか

付録 A〜F をコピーしたあと、**どこに保存すれば効くのか**を説明します。ここを間違えると、書いても一切読み込まれません。

### G-1. ファイルの置き場所

自分のプロジェクトのフォルダを、こう配置します。

```
あなたのプロジェクト/
├── CLAUDE.md                    ← 付録 A をここに保存（★これだけで有効）
├── .claude/
│   └── skills/
│       ├── ja-pdf-export/
│       │   └── SKILL.md         ← 付録 B-1
│       ├── release-guard/
│       │   └── SKILL.md         ← 付録 B-2
│       └── customer-handoff/
│           └── SKILL.md         ← 付録 B-3
├── docs/
│   └── checklists/              ← 付録 D・E・F（置き場所は自由）
└── （あなたのコード）
```

**重要な点は 3 つです。**

| 対象 | 置き場所 | 効き方 |
|---|---|---|
| `CLAUDE.md` | **プロジェクトのルート直下** | **毎回自動で読み込まれる**。設定作業は不要 |
| Skill | `.claude/skills/<名前>/SKILL.md` | **フォルダ名 = Skill 名**。`SKILL.md` というファイル名は固定 |
| チェックリスト類 | どこでも可 | 自動では読まれない。使うとき「`docs/checklists/xxx.md` に従って」と伝える |

`.claude` はドット始まりなので、Mac の Finder では既定で見えません。`Cmd + Shift + .` で表示できます。

### G-2. フォルダを作るのが面倒なら、Claude Code にやらせる

そもそも、この設置作業自体を頼めます。

```
プロジェクトルートに CLAUDE.md を作ってください。
内容は以下です:

（付録 A の中身を貼り付け）
```

Skill も同じ要領です。

```
.claude/skills/ja-pdf-export/SKILL.md を作ってください。
フォルダが無ければ作成してください。
内容は以下です:

（付録 B-1 の中身を貼り付け）
```

### G-3. 効いているかの確認方法

`CLAUDE.md` を置いたら、次のように聞いてみてください。

```
CLAUDE.md を読み込んでいますか？
書かれているルールを 3 つ挙げてください。
```

書いたルールが返ってくれば正しく効いています。返ってこない場合は、**ファイルの置き場所がルート直下になっていない**のがほぼ全ての原因です。

Skill の確認はこうです。

```
利用可能な Skill を一覧で教えてください。
```

### G-4. 最初から全部入れなくていい

**まず `CLAUDE.md` だけ置いてください。** これだけで効果の大半が得られます。

Skill は、実際に「同じ手順を 3 回説明したな」と感じてから作れば十分です。
最初から全部揃えようとすると、使わないルールが混ざって、肝心のルールが薄まります（第 6 章）。

## 14. 結局、何が変わったのか

最後に、1 ヶ月やって思ったことを書きます。

Claude Code で変わったのは、コードを書く速度ではありませんでした。

正直に言うと、コードを書く速度は 3〜5 倍になった程度です。それも十分すごいのですが、決定的ではありません。一人で書いていた頃も、コードを書くこと自体はそこまでボトルネックではなかったからです。

決定的に変わったのは、コード以外の全部でした。

以前の私は、提案資料を作りませんでした。作れなかったというより、機能を作ることで手一杯で、そこまで手が回らなかった。操作マニュアルは後回しにして、結局作らないまま終わる。導入の手順は口頭で説明する。性能を聞かれたら「速いです」と答える。コストはどんぶり勘定。テストは時間がなくて書かない。変更履歴は自分の記憶の中。

今は、提案資料が HTML と PDF で 16 本あって、操作マニュアルは読者別に 5 種類あって、導入手順は依頼書として渡せる形になっていて、性能は 5,000 チャンクで 5ms という実測値があって、コストは 1 質問 2〜3 円という根拠があって、テストは 377 本あって、変更履歴は 222 行の CHANGELOG になっています。

個人で作ったものが会社に売れない理由は、機能が足りないからではないと思うようになりました。周辺が全部足りないからです。資料がない、手順書がない、根拠となる数字がない、テストがない。

Claude Code が本当に埋めたのは、そこでした。

そしてそれを引き出すために要ったのが、この記事に書いた 5 つ——`CLAUDE.md`、Skill、聞き方の型、テスト、そして人間のレビュー工程です。

プロンプトの上手さは、5 分の 1 でしかありませんでした。残りの 5 分の 4 は環境の設計で、そしてそれは 1 日で作れます。

付録のテンプレートは、そのまま使ってください。私が 13 回詰まって、バグを 6 件踏んで、PDF を中国語にして、自分の本名を公開しかけて作ったものです。

同じ道を通る必要はないと思います。
