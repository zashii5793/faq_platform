## 1. 何を作ったのか（前提の共有）

**Inquira** — 社内ドキュメントを根拠に AI が回答する、セルフサービス型 FAQ プラットフォーム。

### 解決した課題

導入先（教育系・従業員 35 名規模）からの相談は、こうでした。

> 「ヘルプデスクのチケットが 1,000 件溜まっている。毎日同じ質問が来て若手が消耗している。
> ChatGPT を使いたいが、社内データを外に出すのは絶対に無理」

この「**同じ質問が繰り返される**」「**でもデータは出せない**」の組み合わせは、業界を問わず存在します。
情シス、学校事務、製造業の現場——構造は同じです。

### 実装した機能（抜粋）

| 機能 | 内容 |
|---|---|
| RAG 回答 | 社内文書を根拠に日本語で回答。出典ファイル・該当セクション・関連度を必ず提示 |
| 確信度スコア | 0〜100% で提示。低い場合は「該当情報なし」と明示して**ハルシネーションを構造的に抑制** |
| 多形式取り込み | PDF / Word / Excel / PowerPoint / CSV / JSON / Markdown |
| PII マスキング | メール・電話・カード番号（Luhn 検証付き）・マイナンバー・IP・URL を送信前に除去 |
| ナレッジ蓄積 | 社員が自分の解決策を共有 → 全社の資産化。入力中に類似質問をリアルタイムサジェスト |
| FAQ 候補抽出 | 繰り返された質問を自動でクラスタリングし「FAQ にすべき質問」を管理者に提示 |
| 回答キャッシュ | 同一質問の再問い合わせで API を呼ばない（API コスト 30〜50% 削減） |
| 管理ダッシュボード | 利用状況・削減効果・質問履歴の全文検索 |
| 認証 | Google OAuth + 許可メール / 許可ドメイン制御 |

### 現在のリポジトリ実数値

私が語る「実績」の根拠を、検証可能な数字だけで出します。

| 指標 | 実数 |
|---|---|
| アプリケーションコード | **6,814 行**（14 モジュール） |
| テストコード | **4,553 行**（20 ファイル） |
| テスト関数 | **377 本** |
| テスト / コード比 | **0.67**（1 行の実装に対し 0.67 行のテスト） |
| カバレッジ | **88%** |
| ドキュメント | **114 ファイル**（Markdown 33 / HTML 17 / PDF 16 / 画像 47） |
| 運用スクリプト | **27 本** |
| CHANGELOG | 222 行（v0.1.0 〜 v0.8.0 の全変更履歴） |
| 検索性能 | 5,000 チャンクで **約 5ms**（p95: 5.4ms） |
| API 実費 | **1 質問あたり 約 2〜3 円** |

**重要なのは 6,814 行という数字ではなく、テストが 4,553 行あることです。**
AI にコードを書かせる開発において、**テストは品質保証ではなく「AI の暴走を検知するセンサー」** として機能します。

## 2. 先に用語だけ — この記事に出てくる専門語の全解説

技術記事は「知っている前提」で進むから読めなくなります。**この記事で使う専門用語を、先に全部ここで説明します。**
読み飛ばして、分からない語が出てきたらここに戻ってきてください。

### 2-1. AI・検索まわり

| 用語 | かみくだいた説明 |
|---|---|
| **LLM** | Large Language Model。ChatGPT や Claude のような「文章を生成する AI」の総称。この記事では Claude を指します |
| **API** | プログラムから外部サービスを呼び出す窓口。「Claude API を呼ぶ」＝自分のプログラムから Claude に質問を投げて答えを受け取ること |
| **トークン** | AI が文章を数える単位。日本語はだいたい **1 文字 ≒ 1 トークン**。料金がこの単位で決まります |
| **RAG** | Retrieval-Augmented Generation。**「まず社内文書を検索して、見つかった文章だけを AI に渡して答えさせる」**やり方。AI に社内情報を覚えさせるのではなく、毎回カンニングペーパーを渡すイメージです |
| **チャンク** | 文書を検索しやすい大きさに切った断片。本システムでは **1 チャンク 600 文字**が上限。「就業規則.pdf」1 ファイルが数十チャンクになります |
| **ハルシネーション** | AI が**もっともらしい嘘をつく**現象。「幻覚」と訳されます。この記事の第 4 章は、ほぼ全部この対策の話です |
| **システムプロンプト** | AI に対する「あなたはこう振る舞ってください」という指示書。ユーザーには見えない、常に効いている前提条件 |
| **プロンプトキャッシュ** | 毎回同じ指示文を送るとき、2 回目以降を割引価格にする仕組み。単価が **約 1/10** になります |
| **TF-IDF** | 古典的な検索アルゴリズム。ざっくり言うと**「この文書にだけ多く出てくる珍しい単語」を重視して探す**方式。AI モデルのダウンロードが不要で軽い |
| **文字 N-gram** | 文章を「2〜3 文字ずつ」に機械的に切って検索する方式。`有給休暇` → `有給`, `給休`, `休暇`… 。**日本語は単語の区切りが無いので、この方式だと辞書なしで検索できます** |
| **形態素解析** | 日本語を単語に切る処理（`有給/休暇/を/申請`）。MeCab などのツールと辞書のインストールが必要 |
| **埋め込み / ベクトル** | 文章を「意味を表す数字の列」に変換したもの。意味が近い文章は数字も近くなるので、**言い回しが違っても意味で探せます**。ただし変換用の AI モデル（数百 MB〜）が必要 |
| **コサイン類似度** | 2 つのベクトルの「向きの近さ」を 0〜1 で測る計算。意味の近さの指標として使います |
| **確信度** | 本システムが独自に算出している「この回答どれくらい信用できるか」の 0〜100% 表示。**AI が自己申告した数字ではありません**（第 4-4 節） |

### 2-2. セキュリティ・個人情報

| 用語 | かみくだいた説明 |
|---|---|
| **PII** | Personally Identifiable Information。氏名・メール・電話番号など、**個人を特定できる情報** |
| **マスキング** | PII を `[氏名]` `[メール]` のような伏せ字に置き換える処理。外部 API に送る前に実施します |
| **Luhn（ルーン）アルゴリズム** | クレジットカード番号が満たす**計算上の法則**。「この数字列は本当にカード番号か」を数学的に判定でき、誤検知を減らせます |
| **XSS** | Cross-Site Scripting。悪意ある人が画面に JavaScript を仕込み、**他人のブラウザで勝手に実行させる**攻撃 |
| **Stored XSS** | 上記のうち、攻撃コードが**サーバーに保存されて全員に配信される**タイプ。最も被害が大きい。第 9 章で実際に見つけたのがこれです |
| **OAuth** | 「Google アカウントでログイン」を実現する仕組み。パスワードを自社で預からずに本人確認ができます |
| **監査ログ** | 誰がいつ何を質問したかの記録。社内ツールでは「後から追跡できること」が導入条件になる場合が多い |

### 2-3. インフラ・導入

| 用語 | かみくだいた説明 |
|---|---|
| **オンプレミス（オンプレ）** | クラウドではなく**顧客の自社サーバー**にインストールして動かす形態。「データを外に出せない」企業向け |
| **FQDN** | `faq.example.co.jp` のような**完全なホスト名**。`10.0.0.5` のような IP アドレスとは別物で、**Google OAuth は IP アドレスを受け付けません**（第 10 章の詰まり #6） |
| **DNS / A レコード** | ホスト名を IP アドレスに変換する仕組み／その対応表の 1 行。社内 DNS への登録は AD 管理者の作業になることが多い |
| **リバースプロキシ** | 利用者とアプリの間に立つ中継サーバー。HTTPS 化や複数アプリの振り分けに使います |
| **IIS / ARR** | Windows Server 標準の Web サーバー（IIS）と、そのリバースプロキシ機能（ARR）。第 10 章の詰まり #13 の犯人です |
| **BOM** | ファイル先頭に付く「これは UTF-8 です」という目印（3 バイト）。**これが無いと PowerShell が日本語を Shift-JIS と誤解して文字化けします**（詰まり #4） |
| **UNC パス** | `\\サーバー名\共有名\フォルダ` 形式の、Windows のファイル共有パス |
| **SPA** | Single Page Application。React / Vue で作る今風の Web 画面。作るには Node.js のビルド環境が必要 |
| **Docker** | アプリを環境ごと箱詰めして動かす技術。便利ですが、**使用を許可していない企業も多い**（詰まり #1） |

## 3. システム構成 — 何を選び、何を捨てたか

技術選定の記事はよくありますが、**「なぜ選ばなかったか」まで書かれているものは少ない**ので、そこを厚めに書きます。

この構成は「技術的に最適」を狙ったものではありません。狙ったのは **「顧客の社内サーバーで、担当者が 15 分でインストールでき、その後の運用を人に押し付けない」** という 1 点です。
その制約から逆算すると、選択肢はかなり絞られます。

### 3-1. 全体像

```
   👤 社員（ブラウザ）
    │
    │ ① 質問を送信
    ▼
 ┌─────────────────────────────────┐
 │  FastAPI サーバー（単一プロセス）      │
 │                                  │
 │  ② 認証チェック（Google OAuth）      │
 │        ↓                         │
 │  ③ PII マスキング ← 送信前に個人情報除去 │
 │        ↓                         │
 │  ④ 検索（TF-IDF / e5 切替可）         │
 │        ↓                         │
 │  ⑤ 確信度スコア算出                   │
 │        ↓                         │
 │   ┌── しきい値未満 → LLM を呼ばず終了 ──┐│
 │   │                              ││
 │  ⑥ 回答キャッシュ確認                 ││
 │        ↓                         ││
 │  ⑦ Claude API（プロンプトキャッシュ）  ││
 │        ↓                         ││

 │  ⑨ 監査ログ記録 ←──────────────────┘│
 └─────────────────────────────────┘
    │
    ▼

   ├ faq_master/        取り込み済みナレッジ (Markdown)
   ├ raw/               アップロード原本 (PDF/Excel/...)
   ├ audit/             監査ログ (JSONL)
   ├ embeddings.npz     埋め込みキャッシュ
   └ *.json             設定・フィードバック・FAQ候補
```

### 3-2. 技術スタックと選定理由

| レイヤ | 採用 | 理由 |
|---|---|---|
| Web フレームワーク | FastAPI + Uvicorn | 単一プロセスで完結。Python だけで動く |
| LLM | Anthropic Claude API | **入力データを学習に使わない**（商用契約で明示） |
| 検索 | TF-IDF (char\_wb 2-3gram) 既定 / multilingual-e5 切替可 | モデル DL 不要で起動できることを既定にした |
| 認証 | Google OAuth (Authlib) | 社内に IDaaS がなくても Google Workspace はほぼある |
| 文書パース | pypdf / openpyxl / python-pptx / pandas | 既存資料をそのまま投入できることが導入の最大要件 |
| 永続化 | **ファイルのみ（DB なし）** | 下記 2-3 で詳述 |
| 設定 | pydantic-settings (`.env`) + 管理 UI からの実行時変更 | 顧客が `.env` を編集せずに済む |

### 3-3. 捨てたもの 4 つと、その理由

ここが構成のいちばん重要な部分です。

#### ❌ 捨てた① データベース

**PostgreSQL も SQLite も使っていません。** すべて `data/` 配下のファイルです。

技術的には DB のほうが優れています。それでも捨てた理由は 3 つ。

1. **顧客に DB 運用を要求しない** — インストール手順に「PostgreSQL のセットアップ」が入った瞬間、担当者の心理的ハードルが跳ね上がる
2. **バックアップがフォルダのコピーで済む** — 「`data` フォルダを既存のバックアップ対象に追加してください」で説明が終わる。`pg_dump` の運用設計を顧客に負わせない
3. **ファイルサーバーの共有パスに置ける** — サーバーを入れ替えてもデータが残る。これは実際に顧客が最も安心した点でした

**トレードオフは正直に書きます。** 同時書き込みに弱く、数百人規模の同時アクセスには耐えません。
ただ、**社内 FAQ の実際の同時アクセスは数人**です。「将来の理論上のスケール」より「今日インストールできること」を優先しました。

#### ❌ 捨てた② ベクトルデータベース

Pinecone も Chroma も Faiss も使っていません。既定は **scikit-learn の TF-IDF** です。

理由は **オフラインで起動できること**。ベクトル検索には埋め込みモデルが要り、初回起動時に数百 MB〜2GB のダウンロードが発生します。
**社内サーバーが外部へ自由に出られない環境は珍しくありません。** そこで止まると導入自体が終わります。

そのうえで、精度が必要な顧客のために**バックエンドを差し替え可能**にしてあります。

```
EMBEDDING_BACKEND=e5-small   # 環境変数 1 つで multilingual-e5 に切替
```

初期化に失敗したら TF-IDF に自動フォールバックする実装にしてあります。**「精度は上げたいが、止まるのは困る」** という顧客の要求はこの形でしか満たせませんでした。

そして実測で、TF-IDF でも **5,000 チャンクの検索が約 5ms**。応答時間の 98% 以上は Claude API の往復なので、**検索を速くしても体感は変わりません**。ここに凝るのは投資先として間違いです。

#### ❌ 捨てた③ 形態素解析器（MeCab / Sudachi）

日本語検索といえば形態素解析、が定石です。使っていません。

代わりに **文字 N-gram（`char_wb`, 2-3gram）** を使っています。

```python
TfidfVectorizer(analyzer="char_wb", ngram_range=(2, 3))
```

理由は導入コストです。MeCab は辞書のインストールが必要で、**Windows Server 上での環境構築が導入の障壁になります**。
文字 N-gram なら、分かち書きなしで日本語をそのまま扱えて、追加インストールがゼロ。

精度は形態素解析に劣ります。それでも、**「入らない 100 点」より「入る 80 点」** を選びました。

#### ❌ 捨てた④ SPA（React / Vue）とビルド工程

フロントエンドは **素の HTML + JavaScript** で、Python 側から文字列として返しています。Node.js を必要としません。

**この判断には明確な代償があります。** `app/main.py` が 4,471 行に膨らんだ主因がこれです（第 9 章で正直に書きます）。

## 4. 何にこだわったか — 「答えないこと」を設計する

機能一覧を見ても伝わらない部分を書きます。**このプロダクトで最も時間をかけたのは、回答精度ではなく「答えない判断」の設計です。**

### 4-1. なぜ「答えないこと」が最重要なのか

社内 FAQ で最悪の事故は、回答できないことではありません。

> **もっともらしい嘘を、自信ありげに答えること。**

「有給の申請期限は 3 営業日前です」と AI が言い、実際は 5 営業日前だった——これが一度起きると、**そのツールは二度と信用されません**。
社内ツールは、一度信頼を失うと使われなくなり、使われなければ存在しないのと同じです。

だから設計目標を、こう置きました。

> **「答えられないときに、正しく黙れること」**

### 4-2. ハルシネーション対策の三重防御

これを 1 箇所の工夫ではなく、**3 段階の独立した防御**にしました。1 つが破られても次で止まります。

#### 防御① 検索スコアが低ければ、そもそも LLM を呼ばない

いちばん確実なハルシネーション対策は、**AI に喋らせないこと**です。

```python
# 確信度: top-1 スコアがこの値未満ならLLM呼び出しを行わず「該当情報なし」を返す
# TF-IDF char_wb の経験値: 関連質問は 0.15+, ノイズマッチは 0.05-0.07 程度
min_score_threshold: float = 0.08
```

コメントの数値は、実データで観測した実測値です。**この 1 行が、精度とコストの両方に効きます**（呼ばない = 課金されない）。

さらに、「ノイズが 1 件だけ強く当たった」ケースを別途弾いています。

```python
# 突出ノイズ判定: top1 が弱く（< 0.12）2位との差が極端な場合のみ
# 0.12 以上は正解1件にヒットしている可能性が高いので回答に進める
if top < 0.12 and len(scored_chunks) >= 2:
    second = scored_chunks[1][1]
    if second / top < 0.3:
        return 0
```

「1 位だけ妙に高くて 2 位以下が全滅」は、**関連文書が本当にある状態ではなく、たまたま文字列が一致した状態**であることが多い——これは実際にログを見て分かったパターンです。

#### 防御② システムプロンプトで「推測の語彙」を名指しで禁止する

ここは何度も書き直しました。最終形の中核はこれです。

```
ルール（厳守）:
1. 提供された [参考情報] に**明示的に書かれている内容のみ**を根拠に回答する
2. [参考情報] に直接の答えが書かれていない場合は、推測せず以下の文言を返す:
   「該当情報が見つかりませんでした。社内ヘルプデスクにお問い合わせください。」
3. 推測表現の使用を禁止: 「だと思います」「おそらく」「一般的には」「〜のはずです」
   「もしかすると」「推察します」など、不確実な語彙は一切使わない
4. 一般常識・あなたの事前知識からの補完を禁止する
   （例: マニュアルに書かれていない手順を「業界の慣習」で埋めない）
5. 回答末尾に出典（ドキュメント名やID）を必ず明記する
```

**ルール 3 が効きます。**
「推測しないで」という抽象的な指示より、**禁止したい語彙を具体的に列挙する**ほうが圧倒的に守られます。
これは Claude Code に対する `CLAUDE.md` の書き方（第 6 章）と、まったく同じ原理です。

**ルール 4 も実戦で必要でした。** AI は親切なので、マニュアルに書いていない手順を「一般的にはこうです」で埋めようとします。
社内規程においては、**一般論は間違いと同義**です。

#### 防御③ LLM の返答を、後段でもう一度検査する

プロンプトで指示しても、破られる可能性はゼロになりません。だから出力側でも検査します。

```python
# LLM が「答えられない」と判断したフレーズ。検出時は sources / confidence を 0 に揃える
_NO_ANSWER_MARKERS = (
    "該当情報が見つかりませんでした",
    "関連する情報も見つかりませんでした",
)
```

なぜこれが要るか。**「該当情報が見つかりませんでした」と答えているのに、画面には確信度 72%・出典 3 件が表示される**——という状態が起きうるからです。
機能としては正しく動いていても、**ユーザーから見れば完全に壊れて見えます**。

**UI に出る全ての信号を、意味的に一致させる。** ここは地味ですが、信頼性の体感を最も左右した部分でした。

### 4-3. 二値ではなく「参考情報」という第三の状態を作った

当初は「答える / 答えない」の 2 状態でした。運用してみると、**この二択が現実に合っていませんでした。**

「直接の答えは書かれていないが、明らかに関連する記述はある」というケースが多いのです。
これを「該当情報なし」で切り捨てると、**目の前にある有用な情報を捨てる**ことになります。

そこで第 3 の状態を作りました。

```python
is_reference = confidence < 50
```

確信度 50% 未満のときは **専用の別プロンプト**に切り替え、こう振る舞わせます。

- 「以下は関連しそうな情報です」と、**公式回答ではないことを明示させる**
- 引用・要約に留めさせ、推測は引き続き全面禁止
- 画面上部に `⚠ 公式FAQ未登録の参考情報です（正確性は保証されません）` を必ず付ける

**「自信の度合いに応じて、話し方を変える」** という設計です。
人間の担当者も「規程にはこう書いてあります」と「たしか関連する話が別の資料にあった気がします」を区別して話します。それを実装しただけとも言えます。

### 4-4. 確信度は「それらしい数字」にしない

確信度は、UI に出す以上は**根拠のある数字**である必要があります。演出で数字を出すのは最悪です。

```python
base = min(95, int(30 + top * 250))
relevant = sum(1 for _, s in scored_chunks if s >= settings.min_score_threshold)
return min(98, base + max(0, relevant - 1) * 3)
```

- 検索スコアから線形に算出
- **上限を 95 / 98 に固定** — 100% は絶対に出さない
- 関連文書が複数あれば少し加点（1 件だけより裏が取れている）

**100% を出さないのは意図的です。** AI の回答に「確信度 100%」と表示されたら、それは嘘だからです。
ユーザーに「必ず出典を確認する」習慣を残すために、上限を開けてあります。

### 4-5. PII マスキング — 本当の敵は「見落とし」ではなく「誤検知」

送信前に個人情報を除去する機能ですが、開発時間の大半は**誤検知の抑制**に消えました。

クレジットカード番号の検出で、こうなったのです。

```
2024-06-24 084412  →  [カード番号]
```

**タイムスタンプが誤検知されました。** 業務ログを取り込むと、これが大量に発生します。
マスキングが過剰だと、**検索に必要な情報まで潰れて回答不能になります**。

対策は 2 段構えにしました。

```python
def _is_likely_credit_card(s: str) -> bool:
    """Luhn + 数字グループ構造で誤検知を抑える厳密判定。

    除外する代表パターン:
      - タイムスタンプ 「2024-06-24 084412」（グループサイズ 4-2-2-6）
      - 4桁未満や8桁超の塊が混ざるもの
    カード番号の典型構造（4-4-4-4, 4-6-5, 16桁連続 等）のみ True。
    """
```

1. **Luhn アルゴリズム**でチェックディジットを検証（カード番号が満たす数学的性質）
2. **数字グループの構造**を検査（`4-4-4-4` のような区切り方をしているか）

そして、モジュールの冒頭にこう明記しました。

```python
実装ポリシー:
- 完全な PII 除去は保証しない（深層モデル必須レベル）。
  "見落とし時の被害を減らす"目的の防御層
```

**できないことを、コードに書いて宣言する。**
「個人情報を完全に除去します」と顧客に説明したら、それは嘘になります。**防御層の 1 枚であると正確に伝えるほうが、長期的には信用されます。**

### 4-6. 「機能として動く」と「運用に耐える」は別物

第 12 章のアンチパターンとも重なりますが、設計上のこだわりとして書いておきます。

埋め込みキャッシュの初期実装は、コーパス全体で 1 つのハッシュキーを作っていました。**機能としては完璧に動きます。**
ただし、1 ファイル追加するたびに全件再計算が走り、**30 分〜2 時間**かかりました。

```python
"""チャンク単位の差分キャッシュ。

旧実装は全チャンクで1つのハッシュキーを作っていたため、1ファイル追加
するだけで全件再エンコードが発生していた（200K chunks で 30分〜2h）。
本実装は (chunk_id, text_hash) → vector をキャッシュし、追加/変更され
たチャンクだけを再計算する。
"""
```

キーの単位を変えただけで、**1 ファイル追加が数秒**になりました。

**「動く」の次に「毎週これを実行できるか？」を問う。** この 1 問を挟むかどうかで、ツールが定着するかが決まります。

### 4-7. フィードバック学習に、あえて上限をかけた

👍👎 を検索スコアに反映していますが、**影響の上限を ±15% に固定**しています。

```python
def _boost_factor(source: str, fb) -> float:
    """フィードバックに基づくブースト係数。
    ネット票数 (up - down) を tanh で滑らかにし、最大 ±15% の倍率に。
    例: net=+5 → ×1.114 / net=-5 → ×0.886 / net=0 → ×1.0
    """
```

`tanh` を使っているのは、**票が積み上がっても効果が飽和する**ようにするためです。

無制限に学習させると、**声の大きい少数の投票で検索結果が支配されます**。
社内ツールでは、これは「特定部署の資料ばかり出てくる」という形で現れます。

**学習機能は、暴走しない上限とセットで初めて機能します。**

### 4-8. 売るために必要だった機能：削減効果の可視化

技術的には地味ですが、**商談で最も効いた機能**なので書いておきます。

```python
# 1質問あたりの「資料を探す or 人に聞く」想定削減時間（分）
minutes_saved_per_answered_query: int = 8
# 共有回答1件あたりの整備時間削減（分）
minutes_saved_per_faq_shared: int = 20
# 平均時給（円）。削減コスト換算用
hourly_rate_yen: int = 3500
```

監査ログから「何件答えたか」を集計し、**削減時間と金額に換算**して管理画面に出します。
しかも **前提値を管理者が変更できる**ようにしました。

これが重要な理由は、**導入を決めた担当者が、社内で成果を説明する必要があるから**です。
「便利です」では稟議は通りません。「月 120 時間、42 万円相当の削減」なら通ります。

**継続利用を決めるのは、使っている社員ではなく、予算を持つ人です。** その人に渡す数字を、プロダクト自身が生成する。
個人開発で企業に売るなら、この視点は機能開発と同じ優先度で持つべきだと思っています。

## 5. 大原則：Claude Code は「速いジュニア 10 人」であって「シニア 1 人」ではない

最初に、この記事全体を貫く認識を共有します。ここを取り違えると、以降のテクニックが全部空回りします。

Claude Code を使った開発で人が失敗する原因は、ほぼ 1 つに集約されます。

> **「優秀なので任せられる」と思ってしまうこと。**

実際の挙動は「シニアエンジニア 1 人」ではなく、**「異常に手が速く、記憶が短く、遠慮がなく、指示された範囲を全力でやるジュニア 10 人」** です。

この認識に立つと、やるべきことが自動的に決まります。

| ジュニア 10 人に対して必要なもの | Claude Code における実体 |
|---|---|
| 就業規則・コーディング規約 | **`CLAUDE.md`** |

| 作業指示書のフォーマット | **プロンプトテンプレート** |
| 成果物の検収基準 | **テスト** |
| 出荷前の最終検品 | **人間のレビュー工程** |

「良いプロンプトを書く」は 5 つのうちの 1 つでしかありません。
**残り 4 つを整備していないことが、AI 開発が散らかる原因のほぼ全て**です。

私はこの 5 つを整備するのに合計で 1 日もかけていません。

## 6. 【最重要】CLAUDE.md — 投資対効果が最も高い 1 ファイル

### 6-1. なぜ CLAUDE.md が効くのか

`CLAUDE.md` はプロジェクトルートに置くだけで、**全セッションの冒頭に自動で読み込まれる**指示書です。

多くの人はこれを「プロジェクト概要を書く場所」だと思っています。**違います。**

> **CLAUDE.md は「過去に起きた事故の再発防止書」です。**

概要を書いても効果はほとんどありません（コードを読めば分かるので）。
効果があるのは、**「AI が放っておくと必ず間違えること」を先回りして禁止する記述**です。

私の運用ルールはシンプルです。

> **同じミスを 2 回説明したら、CLAUDE.md に書く。**

3 回目を説明することは、二度とありません。

### 6-2. 実際に起きた事故と、そこから生まれたルール

私の `CLAUDE.md` に書かれているルールは、全て実際の事故から生まれました。3 つ紹介します。

#### 事故①：PDF が中国語フォントで生成された

顧客に配る操作マニュアルを WeasyPrint で PDF 化したところ、**漢字が中国語書体**で出力されました。
「直」「経」「値」あたりの字形が明確に違い、日本の企業に出す資料としては即アウトです。

原因は、Linux 環境で日本語フォントが指定されていないと、フォントマッチャが **CJK 共通フォントから中国語圏のフォントを優先的に選ぶ**こと。
Mac の開発機では正常に見えるため、**気づかずに顧客へ渡す事故が起きうる**のが最も怖い点です。

これを「毎回指示する」のではなく、ルール化しました。

```markdown
### 日本語フォント (中華フォントへのフォールバック防止)

PDF 化される HTML には、必ず以下の font-family を使用すること。
weasyprint で生成する PDF が中国語フォントにフォールバックする事故を防ぐため、
IPA フォントを明示的に末尾に含める。

​```css
font-family:
  "Hiragino Kaku Gothic ProN",
  "Hiragino Sans",
  "Yu Gothic",
  YuGothic,
  Meiryo,
  "IPAPGothic",
  "IPAGothic",
  sans-serif;
​```

- Mac → Hiragino 系が優先される
- Windows → Yu Gothic / Meiryo が優先される
- Linux (weasyprint) → IPAPGothic / IPAGothic が使用される
  (これを書かないと weasyprint が CJK フォントから中国語フォントを選ぶ事故が起きる)
```

**ポイントは「なぜそう書くか」の理由を併記していること。**
理由を書くと、AI は**類似の状況にルールを応用**します。理由なしの命令は、想定外のケースで破られます。

#### 事故②：顧客の実データをリポジトリに書きそうになった

オンプレ導入の作業中、手順書に顧客の社内ドメイン・社内 IP・ファイルサーバの UNC パス・SSL 証明書の Thumbprint が
そのまま書かれた状態でコミット寸前まで行きました。

これは **AI の責任ではありません。** 私が会話でその値を渡し、AI が親切に手順書へ埋め込んだだけです。
つまり **「渡した情報は成果物に出る」** という当たり前の帰結で、対策は AI 側ではなく運用側に置く必要があります。

```markdown
### 顧客固有情報の取扱

- 顧客名、社内ドメイン、社内 IP、UNC パス、SSL 証明書 Thumbprint 等は **絶対にコミットしない**
- 例示する場合は `<CUSTOMER_DOMAIN>`, `example.local`, `10.0.0.x`,
  `\\fileserver\share\inquira` のような一般的な値を使用
- 実値は `.private/` 配下で管理 (.gitignore 済み)
- コミット前に下記のチェックを実行することを推奨:
  ​```bash
  git diff --cached | grep -iE '<顧客固有語>|192\.168\.|@gmail\.com|sk-ant-|GOCSPX-'
  ​```
```

grep パターンに `sk-ant-`（Anthropic API キー）と `GOCSPX-`（Google OAuth クライアントシークレット）を
含めているのが実務上のキモです。**この 2 つは開発中に最も漏れやすい**。

#### 事故③：資料の文体が「押しつけがましく」なっていた

AI に顧客向けマニュアルを書かせると、**善意で余計なことを書きます。**

> 「ご不明な点は社内の情報システム部門へお問い合わせください」

一見親切ですが、これは **顧客の組織構造を勝手に決めつけている**文章です。
情シス部門が存在しない会社、外部委託している会社では、この 1 行が信頼を削ります。

```markdown
### 「情シス」「弊社」「A 社」等の表現

- 「不明点は社内情シスへ」のような **押しつけがましい表現は使わない**
  (顧客側の組織構造を勝手に決めつけることになる)
- 「弊社」「A 社」のような **特定の組織を指す表現は使わない**
  (汎用テンプレートとして使えなくなる)
- 推奨表現: 「サービス提供元」「本ツールを導入された管理者の方」「サービスご利用元」
```

**この 1 ルールの効果は絶大でした。**
なぜなら、「特定顧客向けに作った資料」が、そのまま「2 社目に出せるテンプレート」になるからです。
**1 社目の納品物が資産になるか、使い捨てになるかは、この文体ルールで決まります。**

### 6-3. CLAUDE.md に書くべき 6 カテゴリ

私の経験上、効くのはこの 6 種類です。逆に、これ以外は書いても薄い。

| # | カテゴリ | 例 | なぜ効くか |
|---|---|---|---|
| 1 | **事故の再発防止** | フォント指定、秘密情報の扱い | AI は同じ罠に必ず再度かかる |
| 2 | **環境固有の罠** | PowerShell は BOM 付き UTF-8、`python3.11` を明示 | AI は一般解を出す。環境の特殊性は伝えないと分からない |
| 3 | **文体・表現の禁止事項** | 「情シス」「弊社」を使わない | AI は善意で余計な断定をする |
| 4 | **バージョニング規約** | `pyproject.toml` と `__init__.py` を同期 | 2 箇所同期は AI が最も忘れる作業 |
| 5 | **記録の義務** | CHANGELOG の `[Unreleased]` に必ず追記 | 1 人開発で最も先に崩壊するのが記録 |
| 6 | **命名規約** | ブランチ `feature/<name>`、タグ `v0.9.0` | 揺れるとレビューコストが増える |

### 6-4. 逆効果になる CLAUDE.md（重要）

やりがちな失敗も書いておきます。

| アンチパターン | なぜダメか |
|---|---|
| **プロジェクトの機能説明を延々書く** | コードを読めば分かる。トークンの無駄で、肝心の禁止事項が埋もれる |
| **「丁寧に書いて」「良いコードを書いて」** | 判定基準がないので何も変わらない |
| **500 行を超える** | 重要度が均され、守られなくなる。**200 行以内が実用限界**（私の実物は約 100 行） |
| **理由を書かずに命令だけ書く** | 想定外のケースで応用が効かず、あっさり破られる |
| **一度書いて放置** | 事故が起きるたびに追記して初めて機能する。**育てるファイル**です |

> 📎 **完全なテンプレート**（注釈付き・すぐ使える形）は
> **付録 A：`CLAUDE.md` テンプレート全文** に掲載しています。

## 7. Skill 化 — 「毎回説明していた手順」を 1 単語にする

### 7-1. Skill とは何で、いつ作るべきか

Skill は、**手順書をファイル化して、必要なときだけ AI に読み込ませる仕組み**です。
`CLAUDE.md` が「常時読まれる憲法」なら、Skill は「必要時に開く業務マニュアル」。

作るべきかの判断基準は 1 つだけです。

> **同じ手順を 3 回説明したら Skill にする。**

`CLAUDE.md` が「2 回」、Skill が「3 回」なのは、**分量の違い**です。
1〜2 行で済む禁止事項は `CLAUDE.md` に、数十行の手順は Skill に。
`CLAUDE.md` に長い手順を書くと、常時読み込みでトークンを食い、他のルールを薄めます。

### 7-2. 私が実際に作った Skill 3 本

実際に効いた 3 本を、**全文そのまま**付録に載せています。ここでは「なぜそれが必要だったか」を書きます。

#### ① `ja-pdf-export` — 日本語 PDF 生成

**必要になった理由**：前述のフォント事故に加え、PDF 生成は「フォント指定」だけでは終わらないため。

実際には毎回、以下を確認する必要がありました。

1. font-family に IPA フォントが含まれているか
2. 生成後に**目視で中文化していないか**（Linux 生成時は特に）
3. A4 に収まっているか（表がはみ出す事故が頻発）
4. 改ページが表の途中で入っていないか

これは 4 ステップの手順であり、`CLAUDE.md` に書くには長すぎます。Skill が正解です。

#### ② `release-guard` — リリース前の防御

**必要になった理由**：1 人開発では、リリース作業が最も雑になるため。

私が実際に何度もやらかしたのは、この 3 つ。

- `pyproject.toml` は上げたが `app/__init__.py` の `__version__` を上げ忘れる
- CHANGELOG に書き忘れる
- `.env` の値をコミットしそうになる

これらは**全て機械的にチェックできる**ので、Skill にして丸投げしました。
「リリースして」の一言で、バージョン同期・CHANGELOG 昇格・秘密情報 grep・テスト実行までが走ります。

#### ③ `customer-handoff` — 顧客配布ドキュメント一式の生成

**必要になった理由**：**これが最も金額的インパクトが大きかった Skill です。**

企業に納品する際、必要なドキュメントは 1 種類ではありません。

| 渡す相手 | 必要なドキュメント | 前提知識 |
|---|---|---|
| 顧客 IT 部門 | インストール手順書 | 高い |
| AD / DNS 管理者 | DNS レコード設定依頼書 | 高い（が、担当が別人） |
| インフラ担当 | リバースプロキシ設定依頼書 | 高い |
| 顧客側の管理者 | 管理画面クイックスタート | 中 |
| 全社員 | 利用ガイド（1 枚） | **ゼロ** |

**同じ製品なのに、5 種類の異なる読者向けに、異なる文体・粒度で書く必要がある。**
これを手作業でやると 1 社あたり数日かかります。Skill 化すれば、**顧客ごとの差分を入力するだけ**になります。

私のリポジトリに PDF が 16 個ある理由がこれです。**AI 開発の本当のレバレッジは、コードより納品ドキュメントにあります。**

> 📎 **Skill 3 本の全文**は **付録 B：Skill 定義集** に掲載しています。

## 8. プロンプト 12 型 — 「なんとなく指示」をやめる

ここが一番「明日から効く」パートです。
1 ヶ月以上、毎日 Claude Code に指示を出し続けて、**明確に出力品質が変わった型**を 12 個に絞りました。

各型に **Before（効かない指示）/ After（効く指示）** を付けます。

---

### 型 1：エラーは「そのまま」貼る（要約禁止）

| | 指示 |
|---|---|
| ❌ Before | 「Python のバージョンエラーが出ました」 |
| ✅ After | ターミナル出力を**一切加工せず全部**貼る |

**なぜ効くか**：エラーログには、あなたが「関係ない」と判断した情報が詰まっています。
実行ディレクトリ、Python のパス、ライブラリのバージョン、スタックトレースの深さ。
**要約は、診断に必要な情報を捨てる行為です。**

私の実例：`cloudflared --version` が `Illegal instruction: 4` で落ちた件。
このエラー文字列を丸ごと貼ったことで、**「Apple Silicon 機に Intel バイナリが入っている」**まで一発で特定できました。
「起動できません」と要約していたら、何往復もしていたはずです。

---

### 型 2：コマンドは「コピペで動く形で」と明示的に要求する

| | 指示 |
|---|---|
| ❌ Before | 「起動方法を教えて」 |
| ✅ After | 「**そのままターミナルに貼って動く 1 行**で。ディレクトリ移動も含めて」 |

**なぜ効くか**：AI はデフォルトで「説明」を返します。「プロジェクトディレクトリに移動して、仮想環境を有効化して…」という文章は、**あなたの脳内で翻訳する工数**を発生させます。

```bash
# ✅ こう返させる
cd ~/faq_platform && PYTHON=python3.11 ./scripts/serve.sh
```

これを毎回要求するのが面倒なら、**`CLAUDE.md` に書けば恒久化します**（これが第 6 章とつながります）。

---

### 型 3：「視覚的に」「HTML で」「PDF で」と出力形式を指定する

| | 指示 |
|---|---|
| ❌ Before | 「導入手順をまとめて」 |
| ✅ After | 「**顧客の IT 部門にそのまま渡せる HTML** で。チェックボックス付き、フェーズごとに色分け、所要時間を明記」 |

**なぜ効くか**：これが**この記事で最も過小評価されているテクニック**です。

Claude Code は、テキストだけでなく **構造化されたビジュアル資料**を作れます。
色分けチェックリスト、フェーズマップ、大きな数字での統計表示、タイムライン。

そして重要なのは、**その成果物が「自分用メモ」と「顧客配布資料」の両方になる**こと。
私のリポジトリの HTML 17 本 / PDF 16 本は、ほぼ全てこの型から生まれています。

**個人開発者が企業に売り込むとき、資料の見た目は技術力と同じくらい効きます。** ここを AI にやらせない手はありません。

---

### 型 4：「いまどこまでやったか」を AI に棚卸しさせる

| | 指示 |
|---|---|
| ❌ Before | （自分で思い出そうとする） |
| ✅ After | 「これまでのやり取りと git 履歴から、**残タスクを優先度付きで整理して**」 |

**なぜ効くか**：AI は git log・CHANGELOG・会話履歴・ファイルの状態を**同時に**参照できます。
人間より正確に棚卸しできる、数少ない領域です。

1 人開発で最も怖いのは「何をやり残したか分からなくなる」ことなので、**週 1 でこれを実行するだけで開発が止まりにくくなります**。

---

### 型 5：フェーズを分割し、「完了報告」を挟ませる

| | 指示 |
|---|---|
| ❌ Before | 「認証機能を作って」 |
| ✅ After | 「フェーズ 1（OAuth 設定）だけやって、**完了したら止まって**。動作確認してからフェーズ 2 に進む」 |

**なぜ効くか**：AI は一気に大量の変更を入れられます。それが問題です。
5 ファイルを同時に変更されてから動かなくなると、**どの変更が原因か切り分け不能**になります。

「速いから任せる」のではなく、**「速いから細かく切る」**。これが逆説的に最速です。

---

### 型 6：スクリーンショットを送る

**なぜ効くか**：Google Cloud Console、Cloudflare、IIS、Windows のダイアログ。
**これらの UI は文章で説明しきれず、しかも頻繁に変わります。**

「同意画面の設定はどこですか」と 3 往復するより、スクリーンショット 1 枚のほうが速い。
特にオンプレ導入では、この差が数時間になります。

---

### 型 7：「これ、Git に push して大丈夫？」を毎回聞く

**なぜ効くか**：AI は `.gitignore` の内容、ステージング中の差分、ファイルの中身を全部読んだうえで判断できます。

これは**チェックリストを人間の記憶に頼らない**という発想です。
第 6 章の「顧客情報の混入」事故以降、私はコミット前にこれを機械的に実行しています。

---

### 型 8：「失敗するテストを先に書いて」と要求する（TDD 強制）

| | 指示 |
|---|---|
| ❌ Before | 「マスキング機能を作って」 |
| ✅ After | 「マスキング機能の**仕様を満たすテストを先に書いて**。失敗することを確認してから実装して」 |

**なぜ効くか**：これが **AI 開発における品質の生命線**です。詳細は第 9 章で書きます。

---

### 型 9：「この設計の欠点を 3 つ挙げて」と批判させる

| | 指示 |
|---|---|
| ❌ Before | 「この設計でいい？」 |
| ✅ After | 「この設計の**欠点を 3 つ**挙げて。特に、規模が 10 倍になったときに壊れる箇所」 |

**なぜ効くか**：AI は既定では同意的です。「いいですね」と返ってきます。
**明示的に批判を要求すると、質が変わります。**

私はこれで「TF-IDF は 1 ファイルの語彙が巨大だと IDF が希薄化して他の文書が検索から落ちる」という指摘を得ました。
これは実際に、**20 万チャンクのチャットログを取り込んだ瞬間に検索精度が全体崩壊する**という形で現実化しました。
事前に指摘されていたので、対処（該当ファイルの隔離運用）が即断できました。

---

### 型 10：「過去の記録から抜粋して」で資料を作らせる

| | 指示 |
|---|---|
| ❌ Before | （週報を自分で書く） |
| ✅ After | 「CHANGELOG と git log から、**今週の成果を顧客報告用にまとめて**」 |

**なぜ効くか**：記録が資産になります。
CHANGELOG を律儀に書く動機が「AI が後で使えるから」に変わると、**記録を書くコストが投資に変わります**。

---

### 型 11：数字を要求する（「速い」を禁止する）

| | 指示 |
|---|---|
| ❌ Before | 「パフォーマンスを改善して」 |

**なぜ効くか**：顧客に「速いです」は通用しません。「5,000 文書で 5ms です」が通用します。
そして**その数字は、あなたが測らない限り存在しません**。

AI はベンチマークスクリプトを書くのが得意です。**測定を頼むことが、そのまま営業資料の作成になります。**

## 9. TDD スプリント — テスト 120 → 377 本、実バグ 6 件検出の実際

### 9-1. なぜ AI 開発でテストが「品質保証」ではなく「センサー」なのか

普通の開発において、テストは品質保証の手段です。
**AI 開発では意味が変わります。**

AI は、あなたが依頼していない箇所も「ついでに」改善します。善意で。
その結果、**別の場所が壊れる**。しかも、あなたはその変更に気づいていない。

つまり AI 開発におけるテストは、

> **「自分が見ていない場所で、何かが壊れたことを知るための警報装置」**

です。この目的が変わると、書くべきテストも変わります。カバレッジ率より、**「壊れたら致命的な箇所を全部押さえているか」**が重要になります。

### 9-2. 実際に回した「TDD スプリント」の手順

私は 2 時間のスプリントで、テストを 120 → 293 本に増やし（現在 377 本）、**実装バグを 6 件発見**しました。手順はこうです。

#### Step 1：攻撃者視点でテストを書かせる（実装は見せない）

```
tests/test_security.py を作って。
このアプリに対する攻撃を想定したテストを書いて:
- XSS（管理画面から保存した値が HTML に反映される箇所すべて）
- SQL/コマンドインジェクション
- 認証バイパス（未ログインで管理 API を叩く）
- パストラバーサル（../ を含むファイル名でアップロード）

重要: 「今の実装が通るテスト」ではなく、
「安全なアプリなら通るはずのテスト」を書いて。
落ちてもいい。
```

**最後の 3 行が決定的です。**
これを書かないと、AI は「現在の実装に合わせたテスト」を書きます。それは何も検出しません。

#### Step 2：落ちたテストを「仕様が正しい」と仮定して修正する

このスプリントで実際に見つかったバグを 1 つ紹介します。

**🔴 Stored XSS（重大度：高）**

管理画面から設定できる「組織名」が、HTML にエスケープなしで埋め込まれていました。

```
再現手順:
1. PUT /api/admin/settings に {"org_name": "<script>alert(1)</script>"} を送信
2. GET / でメインページを取得
3. <p> タグ内に <script>alert(1)</script> が未エスケープで埋め込まれる

影響: 管理画面に値を保存できる者が、全社員のブラウザで任意 JS を実行できる
```

これは**社内ツールだから安全**という油断が生む典型例です。修正は単純でした。

```python
def _esc(s: str | None) -> str:
    """HTML エスケープ（XSS 防止）。組織名等を HTML に埋め込む前に必ず通す。"""
    return html.escape(str(s or ""), quote=True)
```

重要なのは、**このバグを AI が「自分で書いたコードの中から」見つけた**という事実です。
書き手としての AI と、テスターとしての AI は、**別人格として使えます。**

#### Step 3：直せない弱点は `xfail` で「既知」として記録する

すべてを直す必要はありません。私は 3 件を `xfail`（既知の失敗）として残しました。

**これが実務上とても重要です。**
「直せていない弱点がテストとして明示されている」状態は、
「弱点が存在することを誰も知らない」状態より、**桁違いに安全**です。

### 9-3. スプリントの成果（実数）

| 指標 | Before | After |
|---|---|---|
| テスト総数 | 120 | **293**（+144%） |
| カバレッジ | 84% | **88%** |
| 発見した実装バグ | — | **6 件**（全て修正） |
| `app/auth.py` カバレッジ | 59% | **89%** |
| `app/runtime_settings.py` カバレッジ | 62% | **100%** |
| 所要時間 | — | **約 2 時間** |

**2 時間で Stored XSS を含む 6 件のバグを発見・修正。**
これが、AI にテストを書かせる最大の投資対効果です。

### 9-4. 正直に書く：それでも私のコードには負債がある

信頼していただくために、都合の悪い数字も出します。

**`app/main.py` は 4,471 行あります。**

アプリ全体 6,814 行のうち **66%** が 1 ファイルに集中しています。これは明確な技術的負債です。

原因ははっきりしています。**AI は「今あるファイルに追記する」のが最も速く、私がそれを止めなかったから。**
機能追加のたびに main.py が膨らみ、v0.8.0 に到達した時点で 4,471 行になっていました。

**教訓**：AI 開発では、**「どこに書くか」を人間が決めないと、必ず 1 ファイルに集中します。**
「新しい機能は新しいモジュールに」というルールを `CLAUDE.md` に書いておくべきでした。
（これは付録 A のテンプレートには**反映済み**です。同じ失敗をしないでください）

## 10. AI がやってくれない工程 — 「機能完成」と「納品」の間にある壁

ここが、個人開発者が企業案件で最も詰まるポイントです。

私の体感は、こうでした。

> **機能の実装：2 週間**
> **企業で実際に動くまで：さらに 4 週間**

後半の 4 週間に、コードを書く作業は**ほとんどありません**。
そしてこの 4 週間の存在を知らないと、見積もりが 3 倍外れます。

### 10-1. オンプレ導入で実際に詰まった 13 箇所

実際に発生した順に、全部書きます。**これはそのままチェックリストとして使えます。**

| # | 症状 | 原因 | 対策 |
|---|---|---|---|
| 1 | Docker 前提で進めたが「Docker 不可」と途中で判明 | 環境の事前確認不足 | キックオフ前に「Docker 使えますか？」 |
| 2 | Windows Server に Linux 用 `install.sh` を渡そうとした | OS 確認不足 | 「OS は何ですか？」を最初に聞く |
| 3 | 管理者権限がなくタスクスケジューラ登録不可 | 権限確認不足 | 「サーバーの管理者権限ありますか？」 |

| 5 | CMD と PowerShell の構文を顧客が混同 | 案内の曖昧さ | コマンドに必ず「**PowerShell で**」と明記 |
| 6 | Google OAuth が IP アドレスのリダイレクト URI を拒否 | Google の仕様 | 「社内 DNS で FQDN を割り当てられますか？」 |
| 7 | OAuth テストユーザー登録漏れで**全員ログイン不可** | 手順書の欠落 | 提供側の準備リストに必ず含める |
| 8 | DNS 設定権限がない（担当者 ≠ AD 管理者） | 権限分離の見落とし | 「DNS は誰が触れますか？」 |
| 9 | リポジトリに顧客固有値を書いてしまった | 提供側のミス | プレースホルダ運用 + コミット前 grep |
| 10 | Mac から Windows サーバへ ZIP を直接渡せない（RDP 制限） | 転送経路の確認不足 | 最初から GitHub 経由 DL を案内 |
| 11 | `Invoke-WebRequest -OutFile` で **BOM が剥がれて**文字化け | PowerShell 5.1 の挙動 | `(New-Object System.Net.WebClient).DownloadFile(...)` を使う |
| 12 | DNS A レコードを **AD サーバー自身の IP** で登録して接続不能 | アプリサーバと DNS サーバが別マシンである見落とし | 登録後に必ず `nslookup <ホスト名>` で検証 |
| 13 | OAuth で Google に飛ばず自ホストの `/o/oauth2/v2/auth` に 404 | **IIS ARR の `reverseRewriteHostInResponseHeaders` が Location ヘッダの `accounts.google.com` を自ホストに書き換える** | `false` に設定する |

**#13 は、丸 1 日溶かしました。**
リバースプロキシが OAuth のリダイレクト先ホスト名を勝手に書き換えるという挙動は、
症状（自分のサイトで 404）から原因（プロキシのヘッダ書き換え設定）に到達するのが極めて難しい。

この 13 個のうち、**AI に聞いて即解決したのは #4・#11・#13 の 3 つだけ**です。
残り 10 個は「顧客に何を聞いておくべきだったか」の問題であり、**技術ではなく段取りの失敗**です。

## 12. やってはいけないこと（アンチパターン集）

私が実際にやらかしたものだけを書きます。

### ❌ 1. Claude Code が作ったブランチをそのまま使い続ける

ある日 `git clone` したら、`main` に README しかありませんでした。

```bash
$ git clone <repo> && cd <repo> && ls
README.md   # ← 「えっ、コードは!?」
```

実装は全部 `claude/add-roadmap-docs-XXXXX` ブランチにありました。
**便利さに任せていると、「本体がどこにあるか分からない」状態になります。**

対策：**週 1 で main にマージする**。もしくはマージ日を決めておく。

### ❌ 2. 「とにかく全部取り込む」

RAG の精度は、モデルではなく**入力データの質**で決まります。

私はテストで自分のブログのエクスポート（9MB）を取り込んだ瞬間、回答品質が崩壊しました。
該当記事はちゃんと検索でヒットしているのに、**確信度 0%**。

チャンクの中身を見て理由が分かりました。

```html
<p class="p1"><span class="s1">だと思います。</span></p>
<p class="p2">&nbsp;</p>
<li><span class="hatena-asin-detail-label">発売日:</span>
```

**HTML タグとメタデータが本文を埋め尽くしていた。**
検索は単語の出現頻度で効くので、意味のあるキーワードがノイズに沈み、関連度スコアが 0.06 まで落ちていました。

さらに悪いのは、**巨大な 1 ファイルがコーパス全体の語彙を支配し、他の正しい文書まで検索から落とす**現象です。
実データ 200MB（約 20 万チャンク）を投入したときにこれが起きました。

対策：
1. 取り込む前にクレンジング（HTML タグ除去）
2. **精度を壊すファイルは隔離ディレクトリに退避する運用ルール**を作る

**「データは多いほど良い」は、RAG では明確に誤りです。**

### ❌ 3. 全件再計算の設計にする

初期実装では、**1 ファイル追加するたびに全チャンクの埋め込みを再計算**していました。

```
1 ファイル追加 → 30 分〜2 時間   ← 運用不能
```

キャッシュのキーを「コーパス全体のハッシュ」から **`(chunk_id, text_hash)` 単位**に変更しただけで、

```
1 ファイル追加 → 数秒
1 ファイル更新 → 数秒
1 ファイル削除 → 即時
```

**「定期的に文書を追加する」という運用が、これで初めて現実的になりました。**
機能としては最初から動いていたのに、**運用としては破綻していた**典型例です。

### ❌ 4. AI 生成物を人間レビューなしで外に出す

繰り返しますが、これは絶対です。実際に混入したもの：

- **開発者本人の氏名**（会話の文脈から親しみを込めて書かれた）
- 顧客の正式名称の表記ゆれ
- 生成時点で古くなっていた数値

**公開前に人間が見る工程は、削ってはいけません。**

### ❌ 5. CLAUDE.md を書いて放置する

書いた時点では 100 点でも、事故が起きるたびに追記しなければ**すぐに陳腐化**します。
私の運用は「同じミスを 2 回説明したら追記」。**育てるファイルです。**

## 2. ドキュメント / HTML / PDF

### 日本語フォント（中華フォントへのフォールバック防止）

PDF 化される HTML、および社外に渡す HTML には、必ず以下の font-family を使用すること。

## 5. 環境固有の注意（自分の環境に合わせて記述）

- PowerShell スクリプトは **BOM 付き UTF-8** で保存すること

- Python は `python3.11` 以上を明示すること（システム標準の python3 は古い場合がある）

### B-1. `ja-pdf-export` — 日本語 PDF を安全に生成する

````markdown
---
name: ja-pdf-export
description: 日本語の HTML を PDF に変換する。中国語フォントへのフォールバックを防ぎ、A4 レイアウトを検証する。「PDF にして」「PDF 化」「資料を印刷用に」と言われたときに使用する。
---

# 日本語 PDF エクスポート

## 手順

### 1. HTML のフォント指定を確認する

対象 HTML の `font-family` に IPA フォントが含まれているかを確認する。
含まれていない場合は、**変換前に必ず修正する**。

```css
body {
  font-family:
    "Hiragino Kaku Gothic ProN", "Hiragino Sans",
    "Yu Gothic", YuGothic, Meiryo,
    "IPAPGothic", "IPAGothic", sans-serif;
}
```

理由: Linux 環境では、日本語フォントを明示しないと CJK 共通フォントから
**中国語書体が選択される**。Mac の開発機では正常に見えるため、
気づかずに社外へ配布する事故につながる。

### 2. 印刷用 CSS を確認する

以下が含まれていない場合は追加する。

```css
@page { size: A4; margin: 15mm; }
table { page-break-inside: avoid; }
h1, h2, h3 { page-break-after: avoid; }
.page-break { page-break-before: always; }
```

### 3. 変換を実行する

```bash
python3 -c "
from weasyprint import HTML
HTML(filename='docs/<name>.html').write_pdf('docs/<name>.pdf')
"
```

### 4. 生成後の検証（省略禁止）

以下を必ず報告する。

1. 生成された PDF のページ数とファイルサイズ
2. **「フォント指定に IPA フォントが含まれていることを確認済み」** の明示
3. ユーザーへの依頼:
   「PDF を開いて、**漢字の字形が日本語書体になっているか**を目視確認してください。
   特に『直』『経』『値』『骨』の字形を確認すると判別しやすいです」

### 5. 中文化していた場合の対処

システムに日本語フォントが入っていない可能性がある。

```bash
# Debian / Ubuntu
sudo apt-get install -y fonts-ipafont fonts-ipaexfont
fc-list | grep -i ipa   # 導入確認
```

## やってはいけないこと

- フォント指定を確認せずに変換すること
- 「PDF を生成しました」だけを報告して、目視確認の依頼を省略すること
````

### B-2. `release-guard` — リリース前の機械的チェック

````markdown
---
name: release-guard
description: リリース前の安全確認とバージョン同期を行う。「リリースして」「バージョンを上げて」「コミットして大丈夫か」と言われたときに使用する。秘密情報スキャン、バージョン同期、CHANGELOG 更新、テスト実行を含む。
---

# リリースガード

リリース前に、以下を **上から順に** 実行する。1 つでも失敗したら中断し、ユーザーに報告する。

## 1. 秘密情報スキャン（最優先・省略禁止）

```bash
git diff --cached | grep -inE 'sk-ant-|GOCSPX-|AIza[0-9A-Za-z_-]{35}|BEGIN (RSA |EC |OPENSSH )?PRIVATE KEY|password\s*=\s*["'"'"'][^"'"'"']{6,}|192\.168\.[0-9]|10\.[0-9]+\.[0-9]+\.[0-9]'
```

**ヒットした場合は、その時点で中断する。** 自己判断でコミットを進めない。
ヒット箇所を提示し、「これはプレースホルダですか、実値ですか」とユーザーに確認する。

追加で確認する:

```bash
git status --porcelain | grep -E '\.env$|\.pem$|\.key$|/\.private/'
```

## 2. バージョン同期

以下 2 箇所が一致しているか確認する。ずれていたら修正する。

- `pyproject.toml` の `version`
- `<package>/__init__.py` の `__version__`

バージョンの上げ方（Semantic Versioning）:

| 変更内容 | 上げる箇所 |
|---|---|
| 後方互換のないインターフェース変更 | MAJOR |
| 後方互換のある機能追加 | MINOR |
| バグ修正のみ | PATCH |

## 3. CHANGELOG

`CHANGELOG.md` の `[Unreleased]` セクションに、今回の変更が記載されているか確認する。
記載がない場合は、git diff から内容を要約して追記する。

リリース時は `[Unreleased]` を `[<version>] - YYYY-MM-DD` に昇格させ、
新しい空の `[Unreleased]` を上に作る。

## 4. テストと静的解析

```bash
ruff check <package> tests
pytest -q
```

**失敗している状態でリリースを進めない。**

## 5. 報告

以下の形式で報告する。

```
✅ 秘密情報スキャン: 検出なし
✅ バージョン同期: pyproject.toml / __init__.py ともに 0.9.0
✅ CHANGELOG: [0.9.0] - 2026-07-28 に昇格済み
✅ テスト: 377 passed
✅ Lint: エラーなし

次のコマンドでリリースできます:
git tag v0.9.0 && git push origin main --tags
```
````

**同じ製品でも、読者ごとに別のドキュメントを作る。** 1 つの資料を全員に渡すと、

| # | 読者 | ドキュメント | 前提知識 | 分量の目安 |
|---|---|---|---|---|
| 1 | 顧客 IT 部門 | インストール手順書 | 高い | 詳細に。コマンドは全てコピペ可能な形で |
| 2 | DNS / AD 管理者 | DNS 設定依頼書 | 高いが**別担当者** | 1〜2 ページ。依頼内容だけ |
| 3 | インフラ担当 | リバースプロキシ設定依頼書 | 高い | 1〜2 ページ。設定値を表で |
| 4 | 顧客側の管理者 | 管理画面クイックスタート | 中 | 画面ごとに何ができるか |
| 5 | 全社員 | 利用ガイド | **ゼロ** | **1 ページ**。図中心、専門用語ゼロ |

## 書き分けのルール

### 依頼書（#2, #3）で必ず守ること

- **依頼相手は製品を知らない**前提で書く。製品の説明は 2 行以内に留める

- 想定所要時間を明記する（相手が着手判断できる）

### 全社員向け（#5）で必ず守ること

- **専門用語を 1 つも使わない**（「RAG」「LLM」「OAuth」全て禁止）
- 1 ページに収める。読まれない資料は存在しないのと同じ
- 「ログインできないとき」の対処を必ず含める（問い合わせが最も多い）
- **「社内の情シスに聞いてください」と書かない**。顧客の組織構造を決めつけないこと

## 顧客固有情報の扱い

- ドキュメント内の顧客固有値は、必ずプレースホルダにする
  - `<CUSTOMER_DOMAIN>` / `<SERVER_IP>` / `<ADMIN_EMAIL>`
- 実値を埋めた版は `.private/` 配下に出力し、**リポジトリにコミットしない**

```bash
grep -rInE '192\.168\.|@gmail\.com|\\\\[a-z]+\\' docs/
```

## 出力形式

- font-family には必ず IPA フォントを含める

| `CLAUDE.md` | **プロジェクトのルート直下** | **毎回自動で読み込まれる**。設定作業は不要 |
| Skill | `.claude/skills/<名前>/SKILL.md` | **フォルダ名 = Skill 名**。`SKILL.md` というファイル名は固定 |
| チェックリスト類 | どこでも可 | 自動では読まれない。使うとき「`docs/checklists/xxx.md` に従って」と伝える |

`.claude` はドット始まりなので、Mac の Finder では既定で見えません。`Cmd + Shift + .` で表示できます。

### G-2. フォルダを作るのが面倒なら、Claude Code にやらせる

そもそも、この設置作業自体を頼めます。

```
プロジェクトルートに CLAUDE.md を作ってください。
内容は以下です:

（付録 A の中身を貼り付け）
```

Skill も同じ要領です。

```
.claude/skills/ja-pdf-export/SKILL.md を作ってください。
フォルダが無ければ作成してください。
内容は以下です:

（付録 B-1 の中身を貼り付け）
```

### G-3. 効いているかの確認方法

`CLAUDE.md` を置いたら、次のように聞いてみてください。

```
CLAUDE.md を読み込んでいますか？
書かれているルールを 3 つ挙げてください。
```

書いたルールが返ってくれば正しく効いています。返ってこない場合は、**ファイルの置き場所がルート直下になっていない**のがほぼ全ての原因です。

Skill の確認はこうです。

```
利用可能な Skill を一覧で教えてください。
```

### G-4. 最初から全部入れなくていい

**まず `CLAUDE.md` だけ置いてください。** これだけで効果の大半が得られます。

Skill は、実際に「同じ手順を 3 回説明したな」と感じてから作れば十分です。
最初から全部揃えようとすると、**使わないルールが混ざって、肝心のルールが薄まります**（第 6-4 節）。

## 14. おわりに — 個人開発者にとって、何が本当に変わったのか

最後に、1 ヶ月やって得た結論を書きます。

Claude Code で変わったのは、**「コードを書く速度」ではありませんでした。**

正直に言えば、コードを書く速度は 3〜5 倍になった程度です。それも大きいですが、決定的ではありません。

**決定的に変わったのは、「コード以外の全部」の速度です。**

| 領域 | 従来の個人開発 | 実際に起きたこと |
|---|---|---|
| 提案資料 | 作らない（作れない） | HTML/PDF で 16 本 |
| 操作マニュアル | 後回しにして結局作らない | 読者別に 5 種類 |
| 導入手順書 | 口頭で説明 | 依頼書として渡せる形に |
| 性能データ | 「速いです」 | 5,000 チャンクで 5ms という実測値 |
| コスト試算 | どんぶり勘定 | 1 質問 2〜3 円という根拠 |
| テスト | 時間がなくて書かない | 377 本、カバレッジ 88% |
| 変更履歴 | 記憶の中 | CHANGELOG 222 行 |

**個人開発が企業に売れない理由は、機能が足りないからではありません。**
「周辺の全部」が足りないからです。提案資料がない、手順書がない、根拠となる数字がない、テストがない。

**Claude Code が本当に埋めたのは、そこです。**

そして、それを引き出すために必要だったのが、この記事で書いた 5 つ——
`CLAUDE.md`、Skill、プロンプトの型、テスト、人間のレビュー工程でした。

**プロンプトの上手さは、5 分の 1 でしかありません。**
残りの 5 分の 4 は、**環境の設計**です。そしてそれは、1 日で構築できます。

付録のテンプレートを、そのまま使ってください。
私が 13 回詰まって、6 件のバグを踏んで、PDF を中国語にして、実名を公開しかけて作ったものです。

**同じ道を通る必要はありません。**
