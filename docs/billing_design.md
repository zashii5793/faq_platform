# Inquira API 計量・請求設計

> 想定読者: Inquira 提供元（運営）の経営・営業・経理担当
> 目的: Anthropic API の **誰の財布で払うか／いくらでクライアントに請求するか／使用量をどう計測するか** を1か所にまとめる。
> 関連: [docs/api_cost_analysis.md](./api_cost_analysis.md) — 単価とコスト試算 / [docs/operations_design.md](./operations_design.md) — 運用 / [docs/api_key_setup.md](./api_key_setup.md) — API キー取得

## 1. 基本方針 — ハイブリッド API キー

クライアントによって最適解が違うため、3つの選択肢を提示します。
営業初期に合意し、契約書に明記します。

| プラン | 誰の API キーを使うか | 月額固定 | API 実費 | 月の使用量上限 |
|---|---|---|---|---|
| **A. 包括プラン (Inquira-managed)** | 運営マスターキー | 〇〇円 | 含まれる（上限内） | あり |
| **B. 実費連動プラン** | 運営マスターキー（子キー） | △△円 | クライアント実費精算 | なし |
| **C. BYO (Bring Your Own)** | クライアントキー | □□円 | クライアントが Anthropic に直接支払い | なし |

具体額は経営判断のため `〇〇`/`△△`/`□□` プレースホルダ。見積時に確定値を入れます。

### 1.1 プラン選択の指針

| クライアント像 | 推奨プラン |
|---|---|
| 小〜中規模（〜500問/月）、運用シンプルさ優先 | **A. 包括** |
| 質問数が読めない／変動が大きい | **B. 実費連動** |
| 自社で Anthropic 契約済み or 法務要件で Anthropic と直接契約必須 | **C. BYO** |
| 初回 PoC / 無料事例 | A の上限内で運営負担 |

## 2. プラン別の設計詳細

### 2.1 プラン A — 包括（Inquira-managed）

**仕組み**:
- 運営の Anthropic アカウントから子 API キーを発行してクライアント環境に設定
- 月額固定費に「○○問まで含む」と明記
- 上限超過時の挙動を契約で決める（後述の **超過時の選択肢** 参照）

**月額固定費に含めるべきもの**:
- ホスティングサポート
- API 実費（上限分）
- 通常運用サポート（平日 9-18 時）
- アップデート

**超過時の選択肢（契約で1つ選ぶ）**:
1. **自動継続**: 超過分は翌月末締めで実費＋手数料 X% を後請求
2. **ソフトリミット**: 超過すると UI 上で「本日の利用枠を超えました」と表示、翌日復活
3. **ハードリミット**: 超過するとログイン後の質問送信が無効化、運営に増枠依頼が必要

実装は `app/llm.py` の手前で月次カウンタを参照する形になります（将来実装）。

**運営側のリスク**:
- クライアントが想定以上に使うと粗利が削れる
- 上限設定 + 月次でレビューが必要

### 2.2 プラン B — 実費連動

**仕組み**:
- 運営の Anthropic アカウントで子 API キーを発行
- 月末に Anthropic Console から **そのキー単位の使用量** を取得
- 「実費 ×（1 + 取扱手数料率 Y%）」 + 「月額管理費 △△円」 で請求

**請求書イメージ**:
```
2026/06 利用分
  月額管理費                       △△,000 円
  API 実費 (Anthropic より転送)    ¥12,345
  取扱手数料 (Y%)                  ¥   N,NN
  ─────────────────────────────────────
  合計                            ¥XX,XXX
```

**運営側のメリット**:
- 使用量変動リスクをクライアントに転嫁できる
- 規模が大きいクライアントでも粗利が安定

**運営側の負担**:
- 月次の使用量取得・按分・請求書発行

### 2.3 プラン C — BYO (Bring Your Own)

**仕組み**:
- クライアントが Anthropic と直接契約し、自分の API キーを発行
- 運営はそれを `.env` に設定するだけ
- 運営側の請求は「月額管理費 □□円」のみ

**運営側のメリット**:
- API 代の取り扱いリスクがゼロ
- 法務・経理が最もシンプル

**運営側のデメリット**:
- 単価が高く見える（API 代が見えないため）
- クライアント側に Anthropic Console の運用負荷が乗る

## 3. 使用量の計量方法

### 3.1 1次データソース: Anthropic Console

最も正確で、契約上の根拠となるソース。

```
https://console.anthropic.com/ → Usage
```

- API キー単位の月次集計
- 入力/出力/キャッシュ別のトークン数
- 日次グラフでスパイク検知

**運営作業**: 月初に前月分を CSV エクスポート → クライアント別に按分。

### 3.2 2次データソース: Inquira 内監査ログ

クライアントに「使用状況の証拠」を提示するため、サーバー側でも記録：

```
/srv/inquira/data/audit/audit-YYYY-MM-DD.jsonl
```

各行に以下を記録（既存実装で含まれている／追加実装が必要なものを区別）：

| 項目 | 既存 | 用途 |
|---|---|---|
| `ts` | ✅ | 日時 |
| `user_email` | ✅ | 質問者 |
| `event` | ✅ | `query` / `feedback` 等 |
| `question_len` | ✅ | 質問文字数 |
| `answer_len` | ✅ | 回答文字数 |
| `model` | ⚠（要確認） | 使用モデル |
| `input_tokens` | ❌ 追加要 | LLM レスポンスから取得 |
| `output_tokens` | ❌ 追加要 | 同上 |
| `cache_read_tokens` | ❌ 追加要 | プロンプトキャッシュ使用時 |

`input_tokens` / `output_tokens` を `app/llm.py` の応答処理で `usage` フィールドから抽出して監査ログに追加すれば、Anthropic Console と独立に「Inquira 側でも料金を再計算できる」状態になります。これは **クライアントへの透明性確保** に有効です。

### 3.3 月次レポート（運営 → クライアント）

プラン A/B では月次で次の3点を提示します：

```
2026年6月 ご利用レポート — A社様

【利用状況】
  質問総数          1,234 件
  回答できた率        91%
  平均確信度         72%
  
【トップトピック】
  1. 経費精算 (203件)
  2. 有給申請 (157件)
  3. パスワード変更 (88件)

【API 使用量】
  入力トークン       3,210,000  (¥9,630)
  出力トークン         215,000  (¥3,225)
  キャッシュ読込       890,000  (¥267)
  ─────────────────────────────
  API 実費合計                  ¥13,122
```

このレポートは `/api/admin/export` を拡張して PDF 生成するか、運営側スクリプトで Anthropic Console データと監査ログを突合して作る形が想定です。

## 4. 暴走防止

API キー漏洩や悪意あるユーザーによる暴発を防ぐ多層防御：

| レイヤー | 仕組み | 設定箇所 |
|---|---|---|
| Anthropic Console | 月予算アラート + ハードリミット | Anthropic Console → Settings → Usage limits |
| Inquira アプリ | 1ユーザー当たりの分間レート制限 | 将来実装（`app/main.py` のミドルウェア） |
| Inquira アプリ | 月次クォータ + 上限到達時の質問拒否 | 将来実装 |
| 質問キャッシュ | 同一質問は 5 分以内ならキャッシュ返答 | `ANSWER_CACHE_TTL`（既存 `config.py:51`） |
| プロンプトキャッシュ | システムプロンプトをキャッシュ化で最大 90% 削減 | 実装済み or 検討（[api_cost_analysis.md §5.1](./api_cost_analysis.md)） |

**Anthropic Console アラートは必須設定** とし、新規キー発行時のチェックリストに入れます。

```
推奨アラート設定（例）
  Soft limit: 想定月額の 80%（メール通知のみ）
  Hard limit: 想定月額の 150%（API 呼び出し自動停止）
```

## 6. 経理面の論点

### 6.1 立替金 vs 売上

プラン B の API 実費部分は経理上どう扱うか：

| 扱い | メリット | デメリット |
|---|---|---|
| **立替金** (経費を立替えてクライアントに転嫁) | 売上が膨らまず PL がきれい | 実費の領収書/明細をクライアントに開示する必要 |
| **売上** (役務として再販) | 取扱手数料を価格に内包しやすい | 売上が膨らみ、結果的に消費税基準も膨らむ |

税理士と相談の上、契約書の表記を合わせます。本書では「実費連動 × 立替金」の前提で書いていますが、運営の経理ポリシーで決めてください。

### 6.2 消費税の扱い

Anthropic API は海外法人（米国）からの提供のため、リバースチャージ方式での申告が必要な場合があります。月額一定額を超えるクライアントが出てきたら税理士確認。

### 6.3 為替の扱い

Anthropic 請求は USD 建て。月末の TTM か社内レート換算かで、再請求時に差損益が出ます。プラン B では「換算レートは月末 TTM」と契約書に明記すると揉めません。

## 7. 子 API キーの運用

運営マスターキーで一括管理するのではなく、クライアントごとに子キーを発行します。

```
運営 Anthropic 組織
  ├ workspace: inquira-master       ← 開発・運営内部用
  ├ workspace: inquira-a-company    ← A社専用
  ├ workspace: inquira-b-company    ← B社専用
  └ workspace: inquira-demo         ← デモ環境
```

各 workspace で独立に Usage が計測できるため、月次按分が不要になります。
キー漏洩時もそのクライアント分だけ失効すれば済みます。

**運営作業**: クライアント追加時、新しい workspace を作成して子キーを発行。 1Password にバックアップ。
