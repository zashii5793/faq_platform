1. Inquira のサービス内容の概要

Inquira (インクワイラ) は、社内のマニュアル、規程、過去の FAQ などを AI が読み取り、社員からの質問に自然な日本語で回答する社内ヘルプデスク向けのプラットフォームです。Anthropic 社の大規模言語モデル「Claude」を利用し、RAG (Retrieval-Augmented Generation) と呼ばれる手法で、自社のナレッジに根ざした回答を返す仕組みになっています。

RAG とは? AI に質問する際、関連する社内ドキュメントを事前に検索して文脈として渡すことで、汎用 AI でも自社の事情に詳しい回答を得られるようにする手法です。AI を再学習させる必要がなく、ドキュメントを更新するだけで AI の知識も更新できる点が特長です。

主な機能

  • 質問への自動回答 (PDF、Word、Excel、PowerPoint 等から取り込んだ情報を参照)
  • 管理者によるナレッジの一括取り込みと管理
  • Google アカウントによる認証 (許可リスト方式)
  • すべての質問・回答の監査ログ記録
  • 業務インパクトの可視化 (削減工数の試算機能)

2. システム構成

今回の構成は、お客様の社内 Windows Server に Inquira を直接インストールし、社員の方が社内 LAN 経由でアクセスする形としました。全体像は次のようになります。

社員 PC ブラウザ (Edge / Chrome)
↓ HTTPS リクエスト
社内 DNS サーバー inquira.example.local → 10.0.0.10
↓ 名前解決の結果に従いアクセス
Inquira サーバー (10.0.0.10)
IIS (Web サーバー / リバースプロキシ) 受信した HTTPS を内部の Inquira 本体へ転送
127.0.0.1:8000 へ転送
Inquira 本体 (Python / FastAPI) 外部接続: Claude API / Google OAuth
ナレッジ / 監査ログの読み書き
社内ファイルサーバー (データ保存先) ナレッジ、監査ログ、設定ファイルを保管

各コンポーネントの役割

社員 PC (ブラウザ)

社員の方が Microsoft Edge や Chrome などのブラウザから Inquira にアクセスする入り口となります。

DNS サーバー

DNS とは? 「inquira.example.local」のような人間が読める名前 (ドメイン名) を、コンピューターが通信に使う IP アドレス (例: 10.0.0.10) に変換する仕組みです。インターネット上の DNS が google.com を解決するのと同じことを、社内ネットワーク内で行うものを「社内 DNS」と呼びます。今回はお客様の Active Directory サーバーが DNS の役割を兼ねていました。

Web サーバー (IIS)

IIS とは? Internet Information Services の略で、Windows Server に標準で含まれる Web サーバーソフトウェアです。Linux 系の Apache や Nginx に相当します。今回は IIS を「リバースプロキシ」として利用しました。
リバースプロキシとは? ブラウザからのリクエストを一旦 Web サーバーが受け取り、社内ネットワークの内側にある実際のアプリケーションへ転送する仕組みです。利点として (1) HTTPS の処理を Web サーバー側で一括して扱える、(2) アプリケーション本体を外部に直接公開しないためセキュリティが向上する、(3) 将来的にアプリケーションを複数台に分散しやすい、などがあります。

Inquira 本体

Python 製のアプリケーションで、FastAPI というフレームワーク上に構築されています。実際の業務ロジック (質問の受付、ナレッジの検索、Claude API への問い合わせ、回答の生成) を担います。

データ保存先

取り込まれたナレッジ、質問履歴の監査ログ、各種設定ファイルを保管します。お客様の既存のバックアップ運用に乗せるため、社内ファイルサーバーの共有フォルダを保存先に指定しました。

Google OAuth (認証)

社員の方は個人の Google アカウントでログインします。事前に許可リスト (ALLOWED_EMAILS) に登録されたメールアドレスのみアクセスを許可する方式としました。

3. 導入の流れ

3.1 構成の選定

当初は、クラウド型のホスティングサービス (Render) でのデプロイを検討しました。Dockerfile を用意すれば数分で HTTPS 付きの URL が利用可能になり、開発者にとって最も簡便な方法です。

ご相談の中で、お客様より「社内のマニュアルを管理可能な範囲外に置くことは難しい」とのご意向が示されたため、データを社内に閉じたオンプレミス構成への変更を行いました。社内サーバーへの直接インストール方式を採用し、データはお客様のファイルサーバーに保存する設計となりました。

3.2 インストール手順の整備

お客様の IT 部門のご担当者様が、最小限の手順で導入を進められるよう、PowerShell スクリプト (install.ps1) を用意しました。スクリプトが行う処理は以下の通りです。

  1. Python 3.11 以上が利用可能かを確認
  2. アプリケーション一式の配置
  3. Python 仮想環境 (venv) の作成と、必要なライブラリのインストール
  4. 環境変数ファイル (.env) の生成と、安全な乱数による署名鍵の発行
  5. サーバー起動時に自動でアプリケーションが立ち上がる設定

インストール先はユーザープロファイル配下 (%USERPROFILE%\Inquira) に統一しています。これにより管理者権限を持たないアカウントでも導入を進められるようにしました。

4. 導入時のインフラ設定

4.1 社内 DNS への登録

オンプレミス構成では、社員の方がブラウザに入力する URL を、社内 DNS に登録する必要があります。Active Directory が稼働している環境では、DNS Manager または PowerShell から A レコード (ホスト名と IP アドレスの対応) を追加します。 

Add-DnsServerResourceRecordA `
  -ZoneName "example.local" `
  -Name "inquira" `
  -IPv4Address "10.0.0.10"

ここで指定する IPv4Address には、Inquira が実際に動作しているサーバーの IP アドレスを入力します。AD サーバーと Inquira サーバーが別マシンの場合、IP を取り違えやすいため、対象サーバー上で ipconfig コマンドにより事前確認することを推奨します。

4.2 IIS によるリバースプロキシ構成

HTTPS 通信を実現するため、IIS を用いたリバースプロキシ構成を採用しました。手順は以下の通りです。

  1. IIS の役割をインストール
  2. URL Rewrite モジュールをインストール (URL の書き換えを担う拡張機能)
  3. ARR (Application Request Routing) モジュールをインストール (リバースプロキシ機能を提供する拡張機能)
  4. 自己署名 SSL 証明書を発行 (社内利用のため認証局を経由しない方式)
  5. IIS サイトを作成し、HTTPS (443 番ポート) のバインドを追加
  6. web.config にリバースプロキシのルールを記述
  7. ARR のプロキシ機能を有効化

これらをまとめて 1 コマンドで実行する PowerShell スクリプト (setup_iis_reverse_proxy.ps1) を作成しました。次回以降のお客様の導入時にも、同じスクリプトで再現可能な状態にしてあります。

4.3 Google OAuth の設定

Google Cloud Console で OAuth クライアントを作成し、次の項目を設定します。

  • 承認済みリダイレクト URI に https://inquira.example.local/auth/callback を登録
  • テストユーザーに、ログインを許可する社員の方の Gmail アドレスを登録

なお、Google の OAuth は IP アドレスを含むリダイレクト URI を許容しません。社内 DNS で FQDN (完全修飾ドメイン名) を割り当てておくことが、認証機能を利用する上での事前条件となります。

5. 導入時に直面した課題と対処

導入の過程で、いくつかの技術的な課題に直面しました。同じ構成を検討される方の参考のため、特に学びの多かった 4 点を共有します。

5.1 PowerShell スクリプトの文字コードに関する課題

配布した .ps1 ファイルの日本語コメントが文字化けし、PowerShell の構文解析エラーが発生しました。

原因は、Windows PowerShell 5.1 が、BOM (バイトオーダーマーク) のない UTF-8 ファイルを Shift-JIS と解釈する仕様にありました。Mac で作成した UTF-8 (BOM なし) のスクリプトを Windows に送ると、この問題が発生する可能性があります。

BOM とは? ファイルの先頭に置かれる「このファイルの文字コードは UTF-8 ですよ」という目印 (3 バイトの特殊な印) です。多くのテキストエディタは、保存時に BOM を付けるか付けないかを選択できます。
対処: 配布する PowerShell スクリプトには必ず UTF-8 BOM を付与する運用に統一しました。あわせて、GitHub からのダウンロード時に BOM が失われる事象も確認されたため、(New-Object System.Net.WebClient).DownloadFile(...) による取得方法をお客様向け手順書に記載しています。

5.2 HTTP 通信下での OAuth 認証 Cookie の不安定さ

HTTP のままで運用しようとしたところ、Google ログインから戻ってきた後に、認証状態を確認するための Cookie が失われ、エラーが発生しました。

近年のブラウザは、Cookie の SameSite 属性 (サイト間でのリクエスト時に Cookie を送るかを制御する設定) の扱いが厳格化されています。HTTP のクロスサイト遷移時には Cookie が保持されにくい傾向があり、OAuth のように外部サービスを経由する認証フローでは、HTTPS 化がほぼ必須となります。

対処: HTTPS 化を進めることとし、IIS リバースプロキシと自己署名証明書による HTTPS 構成 (前述 4.2) を採用しました。

5.3 DNS A レコードの設定値の取り違え

HTTPS でアクセスを試みたところ、ブラウザがタイムアウトする事象が発生しました。確認したところ、社内 DNS の A レコードが AD サーバー自身の IP を指していて、Inquira が動作しているサーバーの IP には向いていない状態でした。

今回の環境では、DNS を管理されている AD 管理者の方と、Inquira を導入する担当者の方が別の方でした。「Inquira サーバー」と「DNS サーバー」が別のマシンであることが、依頼の際に明確に伝わっていなかったことが直接の原因です。

対処: DNS 設定依頼書のテンプレートに「対象サーバー上で ipconfig により IP を確認する」ステップを追記しました。同様の構成を持つお客様への導入時にも、本ステップを必ず実施するよう運用に組み込んでいます。

5.4 ARR の Location ヘッダー書き換えによる OAuth フローへの影響

HTTPS の疎通は確認できましたが、Google ログインボタンを押下すると {"detail":"Not Found"} が表示される事象が発生しました。

ブラウザの URL バーを確認したところ、本来 https://accounts.google.com/o/oauth2/v2/auth?... に遷移すべきところが、https://inquira.example.local/o/oauth2/v2/auth?... に書き換わっていました。curl による切り分けの結果、Inquira 本体は正しく accounts.google.com を返しており、IIS を経由する段階でホスト名が書き換わっていることが判明しました。

原因は、ARR の reverseRewriteHostInResponseHeaders という設定でした。この設定は既定で有効になっており、レスポンスの Location ヘッダー (ブラウザに次の遷移先を指示するヘッダー) を、自ホスト名に書き換える動作をします。社内アプリ同士を連携させる用途では便利な機能ですが、OAuth のように外部のサービスへリダイレクトするケースでは、外部 URL まで書き換えてしまうため、認証フローが正常に動作しなくなります。

対処: 本機能を無効化する設定を、IIS セットアップスクリプト内に組み込みました。次回以降のお客様の導入時には、同じ事象を未然に防げる状態となっています。 
appcmd set config `
  -section:system.webServer/proxy `
  /reverseRewriteHostInResponseHeaders:"False"

6. 振り返り

6.1 リリース運用の整備

本番稼働後の継続的なバージョンアップを見据え、お客様側で 1 コマンドにより実行可能な更新スクリプト (update_inquira.ps1) を整備しました。スクリプトは、現在のコードのバックアップ、新バージョンへの入れ替え、起動後のヘルスチェック、失敗時の自動ロールバックまでを 1 連の流れで実施します。

あわせて、Semantic Versioning に基づくバージョン管理ルール、CHANGELOG.md での変更履歴管理、タグによるリリース指定の仕組みを整え、エンタープライズソフトウェアとして必要なリリース運用基盤を構築しました。

6.2 ドキュメントの整備

試行錯誤の過程で得られた知見は、社内のナレッジとして以下に整理しました。

  • 導入時の事前ヒアリングシート (お客様の環境確認用)
  • 過去に発生した課題と対策の一覧
  • リリース運用のガイドライン
  • 顧客向け導入手順書のテンプレート

これにより、次のお客様の導入時には、同じ課題を未然に防げる体制が整いました。

6.3 顧客情報の取り扱いに関する反省

社内向け資料の作成過程で、お客様の社内ドメイン名、サーバー IP、証明書情報などを含むファイルを Public リポジトリにコミットしてしまうミスがありました。

発覚後、直ちに該当情報をプレースホルダーに置換し、git の履歴自体を書き換える対応 (git filter-repo によるトークン置換 + force-push) を行いました。再発防止のため、コミット前の検査スクリプトの導入、ドキュメントのテンプレート化の徹底、実値を含むファイルを .private/ 配下で管理する運用ルールを定めています。

6.4 全体を通じた学び

  • クラウドサービスが多くのインフラ要素を抽象化してくれる時代でも、オンプレミス案件では DNS、TLS、リバースプロキシ、ブラウザのセキュリティモデルなどの基礎知識が必須となります
  • 一度発見した課題は、必ずスクリプトやドキュメントに反映し、次の導入時には自然に回避できる状態にすることが重要です
  • 顧客情報の取り扱いは、技術以前のガバナンス課題として、最優先で運用ルールを定める必要があります

まとめ

Inquira のオンプレミス導入を通じて、システム構成全体の設計から、DNS、リバースプロキシ、OAuth 認証まで、多くのインフラ要素について実践的な知見が得られました。本記事が、社内向け AI システムの導入や、Windows Server 上でのアプリケーション運用を検討されている方の参考になれば幸いです。

本記事中に登場する固有名詞、IP アドレス、ドメイン名は、すべて例示用の架空のものです。実際の導入事例を一般化したうえで記述しています。
