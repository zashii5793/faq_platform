オンプレ社内 AI を本番リリースするまでに踏んだ7つの地雷 — インフラ初心者の生存記録

2026-06-15 / Inquira 開発チーム

社内 FAQ AI「Inquira」を、ある顧客のオンプレ Windows サーバーに導入しました。30 分で終わるはずだったのに、結果的に 3 日ハマりました。
本記事は「アプリ屋がインフラに殴られた記録」です。同じことをやろうとしている人が、私と同じ罠を踏まないように、踏んだ地雷を時系列で全部書きます。

1. 何を作っていたか

Inquira は、社内マニュアル・規程・FAQ を AI が読んで質問に答えてくれるアプリです。Python (FastAPI) + Claude API + Google OAuth 認証で動きます。今回はそれを クラウドではなく顧客の社内サーバー (Windows Server) に直接インストールする案件でした。

2. なぜオンプレ? — クラウドではダメだった理由

当初は Render という PaaS にデプロイする予定でした。Dockerfile を push すれば 5 分で HTTPS 付き公開 URL が手に入る、開発者の天国です。

しかし顧客から一言: 「社内のマニュアルを Anthropic 以外に出すリスクは取れない」。これでクラウドは即死。Windows Server へのオンプレ導入に方針転換しました。ここから地雷原です。

3. 罠①: PowerShell が日本語スクリプトを化けさせる

症状 配布した install.ps1 を実行したら「'式の終わりの ')' が存在しません」というパースエラー。コメント文の日本語が文字化けして見える。

原因は文字コードでした。Windows PowerShell 5.1 は BOM の無い UTF-8 を Shift-JIS と勘違いするクセがあります。Mac で書いた UTF-8 BOM 無しの .ps1 を Windows に送ると壊れる。

対策 スクリプトには必ず UTF-8 BOM を付けて配布する。バイナリ先頭の EF BB BF 3 バイトを足すだけ。

さらに罠の中の罠。Invoke-WebRequest -OutFile で GitHub から DL すると、サーバー側に BOM があってもクライアント側で剥がされる。これに気付かず半日溶かしました。 

# BOM が保たれるダウンロード方法
(New-Object System.Net.WebClient).DownloadFile($url, $dest)

4. 罠②: Google OAuth は IP アドレスを拒否する

社内 LAN の IP (例: http://192.168.x.x:8000/) で Inquira を公開して、Google ログインを試したら「アクセスがブロックされました」。

原因 Google の OAuth はリダイレクト URI に http://<IPアドレス>/auth/callback を許してくれない。FQDN (例: inquira.example.local) が必要。
対策 社内 DNS で A レコードを作る。AD サーバー上で: 
Add-DnsServerResourceRecordA `
  -ZoneName "example.local" `
  -Name "inquira" `
  -IPv4Address "10.0.0.10"

クラウドなら勝手に振られる FQDN を、オンプレでは自分で社内 DNS に書きに行く必要がある。これ、知らないとそもそも詰みます。

5. 罠③: HTTPS じゃないと Cookie が不安定

FQDN を割り当てて HTTP で公開。Google ログインまでは進むのに、リダイレクト後に「State mismatch」のエラー。

原因 最近のブラウザは Cookie の SameSite=Lax 仕様が厳しくなっていて、HTTP のクロスサイト遷移 (Google → 自社) で OAuth 状態 Cookie が消える。Edge では特に顕著。
対策 諦めて HTTPS 化。社内環境なので Let's Encrypt は使えず、IIS で自己署名証明書を発行 → リバースプロキシでバックエンド (uvicorn) に転送、という構成にしました。

6. 罠④: IIS リバプロを自動構築する

IIS は手作業だと 30 ステップくらいあるので、PowerShell スクリプトで自動化しました。URL Rewrite + ARR の 2 モジュールを使って、80 → 443 リダイレクト、443 → 127.0.0.1:8000 へリバプロ、自己署名証明書を作って信頼ストアに登録、までを一発実行。

小罠 Microsoft が download.microsoft.com を自動アクセスから 403 ブロックしている時期があり、MSI を curl で取りに行くと死ぬ。
対策 3 段フォールバック設計: 既存インストール検知 → winget install Microsoft.IIS.URLRewrite → 手動 MSI 配置。

7. 罠⑤: DNS A レコードが別マシンを指していた

HTTPS で立てた。ブラウザでアクセス → タイムアウト。

切り分けたら、社内サーバー上で Test-NetConnection inquira.example.local -Port 443 が TCP 拒否。nslookup は解決できる。でも繋がらない。

原因 AD 管理者に DNS を依頼したら、A レコードを AD サーバー自身の IP (10.0.0.20) で登録してしまっていた。Inquira が動いている本物のサーバーは 10.0.0.10。「Inquira サーバー」と「DNS サーバー」が別マシンだという当たり前のことを伝えそびれた。
対策 依頼書テンプレに「Inquira が動くマシンの IP を実機で ipconfig 確認」のステップを明記。AD 管理者と Inquira 担当者が別の場合の典型事故です。

8. 罠⑥: IIS の ARR が accounts.google.com を書き換える

ここまでで HTTPS は通った。本物の「Google でログイン」ボタンを押す。表示は {"detail":"Not Found"}。

ブラウザのアドレスバーをよく見ると https://inquira.example.local/o/oauth2/v2/auth?...。本来は https://accounts.google.com/o/oauth2/v2/auth?... に飛ぶはず。どこかでホスト名が書き換わっている。

切り分け。バックエンドに直接 curl すると正しく Location: https://accounts.google.com/... を返す。IIS 経由だと Location: https://inquira.example.local/...。IIS が外部 URL を自ホストに書き換えている。

原因 ARR の既定値 reverseRewriteHostInResponseHeaders=true が、レスポンスの Location ヘッダを「自ホスト化」する仕様。社内アプリのプロキシでは便利だが、OAuth みたいに外部 IdP にリダイレクトするアプリでは致命傷。
対策 
appcmd set config `
  -section:system.webServer/proxy `
  /reverseRewriteHostInResponseHeaders:"False"
iisreset
これで accounts.google.com がそのまま返るようになり、ログインフローが完走。地雷を踏んだら、必ずセットアップスクリプト本体に修正を組み込んで再発防止です。

9. リリース基盤を整える

動いた瞬間「次のバージョンどうやって届けるか」が次の問題に。社員 20 人が毎日使ってる本番に、コードだけ上書きしたい。ダウンタイムは 1 分以内。

作ったのは scripts/update_inquira.ps1 という 1 コマンド更新スクリプト。

  • GitHub からタグ指定で ZIP を取得
  • 現在のコードを Inquira_backups/<timestamp>-v<旧版>/ に退避
  • .env / .venv / データ保存先は触らない
  • 新コードに入れ替え → pip install -e . → 再起動
  • 30 秒以内に /healthz が 200 を返さなければ自動ロールバック

顧客 IT 部門には「メール 1 通 + コマンド 1 行」で更新が届きます。SemVer + タグ運用 + CHANGELOG.md とセットで、エンタープライズソフトらしい運用が完成。

10. 全体の学び

① インフラを知らないアプリ屋は今すぐ知る

DNS / TLS / リバースプロキシ / ファイアウォール / OS の文字コード。クラウドが全部隠してくれるけど、オンプレに出た瞬間にこれら全部が殴ってきます。最低限の動作原理は知っておきましょう。

② 失敗ログを残す = 次回はハマらない

今回の 7 つの罠は、それぞれ「初めて見た時は 1〜半日溶かした」案件です。記録に残せば、次の顧客導入では各々 1 分で解決できる。学習を文化資産化するか、毎回個人芸で乗り切るかで、3 社目で差が出ます。

③ 自動化スクリプトに「修正」を組み込む

ARR の罠 (罠⑥) のように、手動で 1 回直したら、必ずスクリプトに恒久対策を埋め込む。「直すこと」と「同じ間違いを次の人 (自分含む) がしないようにすること」はセット。

④ 顧客情報は絶対にリポジトリに入れない

今回、一度 Public リポジトリに顧客のドメイン名・サーバー IP・証明書 Thumbprint を含むレポートをコミットしてしまうミスがありました。すぐ気付いて git filter-repo で履歴ごと sanitize → force-push しましたが、こういう事故は秒で起きます。

予防: コミット前の git diff --cached | grep、テンプレ化 (<CUSTOMER_DOMAIN> プレースホルダ)、実値は .private/ 配下で扱う、を徹底。

もし同じ構成をやるなら

  1. 顧客に「サーバー OS / 管理者権限 / Docker 可否 / 既存 DNS 権限」を最初に確認
  2. Inquira サーバーの実 IP を控える (これが次工程全部の起点)
  3. 社内 DNS に A レコード登録 (Inquira サーバーの IP を指定、間違えると罠⑤)
  4. IIS リバプロ用スクリプトで HTTPS 化 (内部で ARR の reverseRewriteHostInResponseHeaders=false を必ず設定)
  5. Google Cloud Console で OAuth テストユーザー登録 + リダイレクト URI 追加
  6. curl.exe -ksi https://<FQDN>/auth/login | grep Location で accounts.google.com が返るのを確認してからブラウザテスト
