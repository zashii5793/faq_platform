# スケーラビリティ・ベンチマーク

> 大量データ投入時の応答時間を実測。顧客説明・SLA設計の根拠データ。
> 計測コマンド: `.venv/bin/python scripts/benchmark_scale.py`

---

## 🎯 結論（先に答え）

| 規模 | 文書数の目安 | 1検索の応答時間 | LLM込みの全体応答 |
|---|---|---|---|
| **小規模** | 〜100文書 | **1ms 未満** | 1.5〜3秒 |
| **中規模** | 〜500文書 | **約 1ms** | 1.5〜3秒 |
| **大規模** | 〜1000文書 | **約 2ms** | 1.5〜3秒 |
| **超大規模** | 〜2500文書 | **約 3ms** | 1.5〜3秒 |
| **巨大** | **5000文書** | **約 5ms** | 1.5〜3秒 |

**結論**: 検索ロジックは 5000文書でも 5ms 未満。応答時間の大半（98%以上）は **Anthropic API の往復**。検索が原因で遅くなるという心配は当面不要です。

## 📊 詳細ベンチマーク（最適化後）

### テスト環境

| 項目 | 値 |
|---|---|
| プラットフォーム | Linux x86_64 |
| Python | 3.11.15 |
| 検索バックエンド | TF-IDF (char-wb 2-3gram) |

実機（Mac M2 / Intel Xeon 等）ではこれよりさらに高速になる傾向です。

起動時に `data/faq_master/` を読んで TF-IDF 行列を作る処理。

| チャンク数 | 構築時間 | 1チャンクあたり |
|---|---|---|
| 100 | 0.01 s | 0.11 ms |
| 500 | 0.05 s | 0.09 ms |

> 💡 5000チャンク（≒ 1000文書 × 5チャンク）でも **起動時に 0.5秒**程度の追加で完了。

### ② 単一検索のレイテンシ

質問1つに対する RAG 検索のみ（LLM 呼び出し前まで）。20回計測の統計値。

| チャンク数 | 平均 | 中央値 | p95（遅い95%カット） |
|---|---|---|---|
| 100 | 0.8 ms | 0.8 ms | 0.9 ms |
| 500 | 1.3 ms | 1.3 ms | 1.4 ms |
| 1,000 | 1.8 ms | 1.8 ms | 2.3 ms |
| 2,500 | 3.1 ms | 3.0 ms | 3.2 ms |
| **5,000** | **5.2 ms** | **5.2 ms** | **5.4 ms** |

> 💡 p95 と平均がほぼ同じ = **応答時間が安定している**（スパイクが少ない）

> 💡 5000文書環境でも **1秒あたり200質問** を捌けます。普通の中堅企業の社内利用なら余裕。

| 0.5KB | 0.1 ms |
| 1.5KB | 0.3 ms |

> 💡 通常の質問（数十〜数百文字）なら **1ms 以下**。100KB を超える巨大な質問は想定外（無視できる）。

### ⑤ フィードバック書き込み時間（既存件数別）

👍/👎 ボタンを押した時の書き込み速度。**既存件数が増えるほど遅くなる**（O(N)）。

| 既存件数 | 書き込み時間 |
|---|---|
| 0 件 | 0.2 ms |
| 100 件 | 0.5 ms |
| 1,000 件 | 3.2 ms |
| **10,000 件** | **34.9 ms** |

> ⚠ **既知の弱点**: ファイル全体の read → modify → write 方式のため線形劣化。
> 100,000 件になると 300ms 超になる見込み。Phase 2 で **SQLite 化を検討**（ROADMAP 参照）。

## ⚡ 最適化の Before / After（参考）

今回のスプリントで以下を改善：

### 改善1: フィードバックスコアの mtime キャッシュ
- 検索ホットパスで毎回 JSON 読み込みしていた → mtime ベースキャッシュ化
- ファイル更新時のみ再読込

### 改善2: フィードバック空のとき boost 計算をスキップ
- フィードバックが空（新規導入直後）は全件の `tanh()` 計算が無駄
- 早期 return で raw_scores をそのまま使う

### 効果

| 項目 | Before | After | 改善 |
|---|---|---|---|
| 検索5000 (avg) | 5.8 ms | 5.2 ms | **-10%** |
| 検索5000 (p95) | 6.8 ms | 5.4 ms | **-21%** |
| QPS 500 | 798 | 905 | **+13%** |
| QPS 5000 | 187 | 200 | **+7%** |
| フィードバック 10K | 43 ms | 35 ms | **-19%** |

## 🚀 全体応答時間の内訳（典型ケース）

5000チャンク環境で 1質問を処理する場合の時間内訳：

```
┌─────────────────────────────────────────────┐
│ ① PIIマスキング           │   0.3 ms        │ 0.02%
│ ② RAG検索                 │   5.2 ms        │ 0.27%
│ ③ プロンプト構築          │   0.1 ms        │ 0.01%
│ ④ Anthropic API 往復       │ 1500-3000 ms    │ 99.5%+
│ ⑤ レスポンス整形・監査    │   1 ms          │ 0.05%
├─────────────────────────────────────────────┤
│ 合計                      │  約 1.5〜3秒     │
└─────────────────────────────────────────────┘
```

→ **応答時間を縮めたいなら、検索ロジックではなく Claude API のモデル選択**で対応するのが王道：
  - `claude-haiku-4-5`: 約 0.5〜1秒（速い、安い、精度やや劣る）
  - `claude-sonnet-4-6`: 約 1.5〜3秒（バランス・推奨デフォルト）
  - `claude-opus-4-7`: 約 3〜6秒（最高精度、コスト高）

## 📈 将来予測

### 文書 10,000本（≒ 50,000チャンク）になったら？

線形補間で予測：

| 項目 | 5,000 | 50,000 (予測) |
|---|---|---|
| インデックス構築 | 0.44 s | **約 4.5 s** |
| 単一検索 | 5.2 ms | **約 50 ms** |
| QPS | 200 | **約 20** |
| メモリ | 23 MB | **約 230 MB** |

→ **このスケールでもまだ快適**。本番運用上限は **50,000チャンク（≒ 10,000文書）程度**を想定して問題なし。

### それを超える場合（100,000チャンク以上）

- TF-IDF → **Embedding（e5-large等）** への切替で大規模 + 高精度
- `EMBEDDING_BACKEND=e5-large` を `.env` で設定
- ただし初回起動時に 2.2GB のモデルダウンロード + メモリ4-6GB 必要
