## なぜ作ったか — どこの会社にもある問題

> 「社員からの問い合わせが多くて、ヘルプデスク担当の手が空かない。
> ChatGPT に資料を学習させて答えさせたいんだけど、機密情報が漏れるのが怖い」

これ、**完全にあるある** です。

整理すると：
- 社員が聞きたい質問 → 資料を読めば書いてある
- 資料はあるが、どこにあるか分からない or 探すのが面倒
- 同じ質問がヘルプデスクに何度も飛んでくる
- 新人は「先輩に聞かないと分からない」状態
- ChatGPT に丸投げすると **機密情報が学習されるリスク**

ヘルプデスクや人事の方なら共感していただけるはず。

---

## 解決の設計：「学習」ではなく「参照」

ここが**一番重要な設計判断**です。

### よくある誤解

「AI に資料を学習させる」と聞くと、こういうイメージを持たれる方が多い：

```
全文書 5GB ──→ AIモデルに焼き込む ──→ 賢いAI誕生
```

これは技術的には Fine-tuning と呼ばれるアプローチで、確かに可能ですが：

- 焼き込み（学習）に時間とコストがかかる（数時間〜数日）
- 一度焼き込むと、文書を更新しても古い情報が残る
- AIモデルに情報が混ざるので、削除しづらい
- **機密情報がモデル経由で他人に出てしまう事故リスク**

### Inquira が採用した設計：RAG（Retrieval-Augmented Generation）

```
[文書] ──保管──► 自社の倉庫（DB）
                    ▲
                    │ 質問のたびに「関連箇所だけ」取り出す
                    │
                 Claude AI
                    │
                    │ 取り出した文書 + 質問 を見て回答
                    ▼
                出典付きの回答
```

**メリット：**
- 文書の更新が即反映（再学習不要）
- AIに情報を「覚えさせない」ので、削除や差し替えが容易
- **出典が明示できる**（どこから引っ張ってきたか分かる）
- Anthropic の商用 API は学習に使われない契約 → **データが他人に流出しない**

### 図書館の例えで言うと

| 学習方式 | 参照方式（Inquira） |
|---|---|
| 司書（AI）に全本を丸暗記させる | 司書は固定。**本棚と検索カードを賢くする** |
| 暗記後は本を捨てても答える | 本がないと答えられない（=本を更新すれば即反映）|
| 何ページに書いてあるか言えない | 「○○.pdfのp.3です」と言える |

「**取り込んだ瞬間から AI が参照できるようになる**」という意味では、これも一種の「学習」と呼んで差し支えないと思っています。

## 技術選定の理由

| 選んだもの | なぜ |
|---|---|
| **Anthropic Claude** | 学習に使われない契約・日本語精度高い・長文に強い |
| **FastAPI** | Python だと AI ライブラリが豊富 + 型安全・速い |
| **TF-IDF（デフォルト）** | モデル DL 不要・即起動・PoC 用に十分 |
| **multilingual-e5（オプション）** | 本番運用で精度を上げたい時に切替可能 |
| **Markdown（FAQ保存）** | 人間が読み書きしやすい・Git で差分追跡できる |
| **JSONL（監査ログ）** | 1行追記で済む・既存ツールで扱いやすい |
| **Google SSO** | パスワード管理リスクをGoogleに任せられる |
| **Docker compose** | 環境差分を最小化、`docker compose up` で起動完了 |

## 設計上の3つのこだわり

### こだわり1：ハルシネーション抑制を「3層防御」で実装

普通の AI チャットボットの最大の問題は「**知ったかぶり**」です。
Inquira は3層で防御：

#### 第1層：スコア閾値で LLM を呼ばない

```python
if top_score < 0.08:
    return "該当情報が見つかりませんでした"
```

検索結果のスコアが低ければ、そもそも Claude を呼ばない。これが**最強の抑制**です。LLM が呼ばれないので絶対に推測できません。

#### 第2層：システムプロンプトで推測を明示禁止

```text
ルール（厳守）:
1. 提供された [参考情報] に明示的に書かれている内容のみを根拠に回答する
2. [参考情報] に直接の答えが書かれていない場合は、推測せず以下の文言を返す:
   「該当情報が見つかりませんでした。社内ヘルプデスクにお問い合わせください。」
3. 推測表現の使用を禁止: 「だと思います」「おそらく」「一般的には」「〜のはずです」
4. 一般常識・あなたの事前知識からの補完を禁止する
```

#### 第3層：確信度スコアの可視化

回答に**確信度バッジ（高=緑/中=黄/低=橙/不可=赤）** をつけて、ユーザーに「どれくらい信じていいか」を提示。

#### 効果

タカヤモーター用 27 質問でベンチマーク：
- 関連質問の正解率: **71%**
- ノイズ抑制（無関係な質問を「該当情報なし」にする）: **100%**
- **総合精度: 74%**（TF-IDF）

「料理のレシピ」「今日の天気」のような無関係な質問は**完璧に弾けます**。

### こだわり2：データ取り込みを「チャンク単位」で扱う

機密情報が混ざった文書を取り込みたい時、ありがちな実装は「ファイル全体を取り込むか・しないか」の二択。

Inquira は**チャンク（段落）単位**で：

- ファイル全体の判定（緑/黄/赤）
- **各チャンクの個別判定**
- チェックボックスで個別 ON/OFF
- 一括操作: 全取り込み / 要確認除外 / 危険のみ除外 / 全スキップ

例えば、「マイナンバーが3行混じった社員リスト CSV」を投げた場合：
- ファイル全体は「🔴 取り込み非推奨」
- 各行が「🔴 危険」
- 取り込みボタンが**自動で無効化**

→ 法務的にも安心。誤って取り込めない設計。

### こだわり3：「使うほど賢くなる」フィードバック学習

回答に対する 👍/👎 を、検索ランキングのブースト材料に使う：

```python
boost_factor = 1.0 + 0.15 * tanh(net_votes / 5.0)
```

- 👍が多い文書 → 最大 ×1.15 倍ブースト
- 👎が多い文書 → 最大 ×0.85 倍に減衰

これで、**人気文書が上位に・役立たない文書が下位に** 自動で動く。

「Fine-tuning ではなく学習しない」と言いつつ、**RAG 層では立派に学習している**わけです。

## セキュリティ三重防御

### 第1層：誰が使うか（認証・認可）
- Google SSO
- 許可ドメイン制（`@example-edu.co.jp` など）

| 元 | マスク後 |
|---|---|

| `03-1234-5678` | `[電話番号]` |
| `1234 5678 9012` | `[マイナンバー]` |
| `××学園の山田先生` | `[学校名]の山田先生`（教育プリセット時） |

- API ログ保持: **7日**で自動削除（より厳しいなら ZDR 契約）
- FAQ 本文・監査ログは **自社サーバ**にしか保存されない

## 学び・反省

### 学び1：「動かない」を価値にする

最初は「答えられないとマズい」と思っていましたが、実は逆。
**「分からない時は分からないと言う」のが最大の差別化**でした。

ChatGPT 系ツールが「適当に答えてしまう」問題を、Inquira は構造的に解決しています。

### 学び2：仕様書 → モックアップ → 実装 のサイクルが速い

ユーザーが「こうしたい」と言ったら：
1. **仕様書**を書いて合意（30分）
2. **静的モックアップ HTML**で見せて合意（1時間）
3. **実装** + テスト（半日〜1日）

の3段階が、私のような状況で一番早い。
「いきなり実装」だと修正コストが高すぎ、「議論だけ」だと前に進まない。

### 学び3：チャンクサイズは小さい方がいい

最初は 600 文字で実装していましたが、これだと「1文書 = 1チャンク」になりがちで、検索精度が落ちる。
**350文字 + 見出し境界で分割**に変えたら、精度が大きく改善（63% → 74%）。

### 反省1：VPN文書を作り忘れた

タカヤモーター用 FAQ 10本を用意した時、なぜか **VPN接続マニュアルを忘れていた**。
実用テストで「VPN繋がらない」が NO_ANSWER になって発覚。

逆に言うと、**ハルシネーション抑制設計が完璧に動いた証拠**でもありますが、テスト前にコンテンツの抜け漏れチェックは必須。

### 反省2：突出ノイズ判定が広すぎた

「`top1<0.18` かつ `top2/top1<0.3` で NO_ANSWER」という閾値で実装していたら、**正解1件だけにヒットする正常な質問** まで弾いていた（誤発動 9件 / 24件）。

`top1<0.12` に絞り込んだら 6件に改善。**仕様書段階で読んでいたつもりでも、実データで動かさないと閾値の最適化はできない**。

### 反省3：ローカルで動かない問題に時間を取られた

ユーザーの Mac が Python 3.9 で、`pyenv install 3.11` のビルドが終わらない問題が発生。
**最初から `uv` か `Docker` を勧めればよかった**。pyenv は Mac だと openssl コンパイルで時間がかかりすぎる。

→ 最終的には Docker 化 + uv 案内 + 既存 Python 利用 の3パターン提供。

## まとめ

「社内 FAQ を AI で」というだけなら他にも選択肢はあります。
ChatGPT Enterprise、NotionAI、Glean などなど。

しかし、Inquira は以下の点で **中堅企業の「機密性は譲れない、SaaSベンダーは怖い」セグメント**にフィットすると考えています：

1. **データ主権** — 自社ホスト可、Anthropic 学習なし契約
2. **業界特化** — マスキング・用語辞書を業界別にプリセット可能
3. **既存資料が即使える** — Notion等への移行作業不要
4. **「分からない」を正直に言える** — ハルシネーション抑制
5. **3日で本番化可能** — Render デプロイ + Google OAuth で30分

3日で作ったプロダクトを、これから「使われるプロダクト」に育てていきます。

導入相談・PoC 希望の企業様、お気軽にお声がけください。
