## 1. 目的

教育系A社様の社内ヘルプデスク業務を効率化するため、過去のチケット履歴・社内ドキュメントを基にした **社内向けFAQ検索／自動回答ツール** を構築する。

### 解決したい課題
- 同種の問い合わせが繰り返し発生し、対応工数を圧迫している
- ナレッジが個人のメール・チャット・チケットに散在している
- 新人が過去事例にアクセスする手段が乏しい

### 成功指標（案・TBD）
- ヘルプデスクへの一次問い合わせ件数を **30%削減**
- 新人の自己解決率を **50%以上**
- 利用者の体感として「役に立つ」と回答 **70%以上**

## 2. 対象ユーザー

| 区分 | 想定人数 | 役割 |
|---|---|---|
| 一次利用者 | 20〜50名（基準35名） | 教育系A社 社内スタッフ |
| 管理者 | 2〜3名 | FAQ メンテナンス、利用ログ確認 |
| 開発／運用 | 1〜2名 | システム保守、Anthropic API キー管理 |

**除外**：学校（顧客）側のエンドユーザーは対象外。社内スタッフ専用ツールとする。

## 3. 機能要件

### 3.1 必須機能（PoC スコープ）

| ID | 機能 | 説明 |
|---|---|---|
| F-01 | 自然言語Q&A | 自由記述で質問入力 → Claude が関連チャンクを参照して回答 |
| F-02 | 出典表示 | 回答に「参考にしたチケットID／ドキュメント名」を必ず付与 |
| F-03 | Google SSO ログイン | 教育系A社社員の Google アカウントのみアクセス可 |
| F-04 | 許可グループ制御 | `faq-users@example-edu.co.jp` 等の Google グループで管理 |
| F-05 | 質問ログ保存 | 誰が・いつ・何を聞いたかを社内DBに記録 |
| F-06 | フィードバック | 回答に👍／👎を付けられる |

### 3.2 拡張機能（本番フェーズ）

| ID | 機能 | 説明 |
|---|---|---|
| F-11 | 管理画面 | FAQ マスター文書のアップロード／削除／更新 |
| F-12 | カテゴリ絞り込み | 出願 / 出席 / 成績 など機能分類でフィルタ |
| F-13 | 類似質問サジェスト | 入力中に「こんな質問が過去にありました」表示 |
| F-14 | エクスポート | 質問ログのCSV出力（管理者向け） |

### 3.3 やらないこと（明示）
- ❌ 学校側エンドユーザーへの開放
- ❌ チケット起票の自動化（既存システムに任せる）
- ❌ 画像／キャプチャの解析（当面テキストのみ）
- ❌ Slack ボット連携（将来検討）

## 4. 非機能要件

### 4.1 性能
- 応答時間：質問送信〜回答開始まで **3秒以内**（ストリーミング想定）
- 同時利用：ピーク時 **5並列** で劣化なし

### 4.2 可用性
- 平日 9:00〜19:00 の稼働率 **99%** 目標（PoC では SLA なし）

### 4.3 セキュリティ（最重要）
- **データはAnthropic学習に使用されない**：商用 API 経由のみ使用（個人プラン禁止）
- API ログ保持：**7日間**（2025/9 以降の標準）。さらに厳格にする場合は **ZDR契約** を検討
- 通信：すべて **HTTPS**
- 認証：**Google Workspace SSO**（OAuth 2.0）
- 認可：**Google グループメンバーシップ**で制御
- 追加防御：**社内ネットワーク IP 制限**（推奨、実施 TBD）
- API キー：環境変数管理、ソースコードへの直書き禁止

### 4.4 データ取り扱い
- **保存場所**：FAQ マスター文書とログは社内サーバ／契約済みクラウドのみ
- **送信制御**：質問時に関連チャンクのみAPI送信（RAG構成、文書全件送信は禁止）
- **マスキング**：学校名・生徒個人情報の検出と除去機構を送信前に挟む（実装 TBD）

### 4.5 監査
- 全リクエスト（質問／管理操作）をログ記録：タイムスタンプ・ユーザー・操作・対象
- 監査ログのエクスポート機能（管理者向け）

## 5. データソース

### 5.1 一次ソース：チケット履歴
- ファイル：`DBチケット履歴.csv`（現状約1,000件）
- **既知の品質課題**：
  - キャプチャ画像は別Path（`\\file\area1\システム_学校_2016\...`）格納 → **当面除外**
  - 問い合わせ内容に「何を／いつまでに／どうしたいか」が不足
  - 解決方法未記載のチケットが多数

### 5.2 クレンジング方針
1. **全件FAQ化はしない**（パレート原則：上位2〜3割で8割カバー）
2. Claude による自動分類で 1,000件 → 50〜100クラスタに圧縮
3. クラスタ単位で人手レビュー（現場メンバー想定）
4. クレンジング後の「正本」を別フォルダで管理し、FAQツールはそちらを参照

```
[元データフォルダ] → クレンジング → [FAQマスターフォルダ] ← FAQツールが参照
```

### 5.3 並行課題：チケット運用ルール改定
- 担当窓口の方起案：今後はチケットに解決内容を記載する運用に変える
- FAQ ツール構築 = チケット運用改善とセットで進める

### 5.4 Google Drive 連携（将来）
- マスター文書を Google Drive に置き、API で定期同期する構成も検討
- PoC ではローカル／社内サーバ上のフォルダで開始

## 6. システム構成（案）

```
[社員ブラウザ]
   ↓ HTTPS
[社内Webアプリ (FastAPI)]
   ├─ Google OAuth 認証
   ├─ 許可グループ確認
   ├─ マスキング処理
   ├─ ベクトル検索（RAGインデックス）
   └─ Anthropic API 呼び出し（Claude Sonnet 4.x）
   ↓ ログ
[社内DB (PostgreSQL or SQLite)]

[FAQマスターフォルダ] → 定期インデックス化バッチ → ベクトルストア
```

### 技術スタック（提案）
- **言語**：Python 3.11+
- **フレームワーク**：FastAPI
- **LLM**：Anthropic Claude Sonnet 4.x（API 経由）
- **Embedding**：OpenAI `text-embedding-3-small` または `intfloat/multilingual-e5-large`（要選定）
- **ベクトルストア**：当初は SQLite + sqlite-vss / chroma などのローカル簡易DB
- **認証**：Google OAuth 2.0（`google-auth-oauthlib`）
- **フロント**：HTMX + Tailwind（軽量）または Next.js（フル SPA）— TBD
