# Inquira 製品化・収益計画書

> **想定読者**: 提供元の経営判断者（＝本プロダクトの意思決定者）
> **目的**: 「クラウド提供（APIキーは顧客持ち）」と「ローカルサーバー導入（導入費＋運用のワンセット販売）」の
> 2 SKU で **収益が見込めるか** を判定し、**限られた人的リソースでどう展開するか** を計画に落とす。
> **初版**: 2026-07-28
> **関連**: [ROADMAP.md](../ROADMAP.md) / [billing_design.md](./billing_design.md) / [api_cost_analysis.md](./api_cost_analysis.md) / [operations_design.md](./operations_design.md) / [deployment_lessons_learned.md](./deployment_lessons_learned.md)

---

## 0. 一行結論

> **収益は見込める。ただし上限を決めているのは市場ではなく「人的リソース」。**
> ローカルサーバー導入は **粗利が厚いが受注できる社数に物理的な上限がある（同時 6〜8 社）**。
> クラウド提供は **1 社あたりの単価は低いが人手をかけずに積み上がる**。
> したがって **「ローカル導入で稼ぎ、その利益でクラウドの自動化に投資する」** 二段構えが唯一現実的な道筋であり、
> **24 ヶ月で月商 80 万円前後（標準ケース）** が妥当な着地見込み。
> 逆に **オンプレを 8 社を超えて受注すると運用だけで手が埋まり、成長が止まる**（第 4 章）。

## 1. 本書が置いた前提

指示内容から以下を前提として読み替えている。認識が違う場合はここを直せば以降の試算も連動する。

| # | 前提 | 根拠・補足 |
|---|---|---|
| 1 | **SKU-A（クラウド提供）** = 提供元がサーバーを持ち、複数社を同居させる。**Anthropic API キーは顧客が自分で契約して持ち込む（BYO）** | 指示「SaaS 系　API キーは顧客のを利用」より。既存 [billing_design.md](./billing_design.md) の「プラン C」に相当 |

## 2. SKU 定義

### 2.1 SKU-A — Inquira Cloud（提供元ホスティング / 顧客 API キー）

| 項目 | 内容 |
|---|---|
| 設置場所 | 提供元が管理する 1 台の VPS に、顧客ごとにコンテナとデータ領域を分離（`deploy/multi-tenant/` が雛形） |
| API キー | **顧客が Anthropic と直接契約し、キーを持ち込む** |
| API 実費 | 顧客が Anthropic に直接支払い（提供元は一切触らない） |
| 提供元の変動費 | サーバー按分のみ（1 社あたり月 500〜1,500 円） |
| 想定顧客 | 30〜100 名。自社サーバーを持たない／情シス専任がいない企業 |
| 提供元の運用工数 | **月 0.5〜1 時間/社**（外形監視 + 問い合わせ対応） |

**この SKU の本質**: 提供元が API 費用の変動リスクを一切負わない代わりに、**顧客に「Anthropic の契約」という宿題を出す**構造。
月額は純粋に役務・ソフトウェア利用料であり、粗利率は 90% を超える。

### 2.2 SKU-B — Inquira OnPrem（ローカルサーバー導入 + 運用ワンセット）

| 項目 | 内容 |
|---|---|
| 設置場所 | **顧客の社内サーバー**（Windows Server / Linux いずれも実績あり） |
| API キー | 顧客が Anthropic と直接契約（SKU-A と同じ BYO） |
| 販売形態 | **初期導入費（一括）＋ 月額運用費（12 ヶ月契約）のセット販売** |
| 初期導入費に含む | 事前ヒアリング、環境構築、Google OAuth 設定、DNS/HTTPS 設定、初期文書取り込み、管理者レクチャー、稼働後 30 日のハイパーケア |
| 月額運用費に含む | 外形監視、バージョンアップ提供と適用支援、平日 9-18 時の問い合わせ対応、四半期ごとの回答精度レビュー |
| 想定顧客 | データを社外に出せない規制業界・情シスが自社サーバーを運用できる企業 |
| 提供元の運用工数 | **月 2〜4 時間/社**（+ 導入時に一括で 3〜8 人日） |

**この SKU の本質**: 単価は SKU-A の 2〜3 倍取れるが、**投入する人時間も 4〜6 倍**。
`docs/deployment_lessons_learned.md` に記録された「ハマリポイント 13 件」（Docker 不可、PowerShell の文字化け、IIS の ARR がリダイレクトを書き換える、AD の DNS 権限分離 …）は、
この SKU が本質的に高タッチであることの実測証拠であり、**標準化投資の対象そのもの**である。

### 2.3 【決定事項の提案】API キーは両 SKU とも BYO に一本化する

現行 [billing_design.md](./billing_design.md) は「A. 包括 / B. 実費連動 / C. BYO」の 3 プランを併記しているが、
**人的リソース制約下では A と B は採るべきでない**。理由は収益性ではなく工数である。

| 廃止すべき理由 | 具体的に消える作業 |
|---|---|
| 月次の使用量按分が不要になる | Anthropic Console から CSV を落として顧客別に割り振る作業（月 1〜2 時間 × 社数） |
| 立替金／売上の経理論点が消える | 税理士確認、請求書の実費内訳作成 |
| 為替差損益の管理が消える | USD 建て請求の月末 TTM 換算、契約書への換算レート明記 |
| 消費税リバースチャージの検討が消える | 海外役務提供の申告論点 |
| 変動リスクがゼロになる | 質問数が急増した月の持ち出し |

**代償**: 顧客から見た月額が「API 込みの総額」より高く見える／顧客に Anthropic 契約の手間が発生する。
→ 対策は §7 の改修バックログ B-1（キー設定 UI）と B-2（無料トライアル用の上限付きキー）で吸収する。

## 3. ユニットエコノミクス

### 3.1 推奨価格（税別・要経営判断）

| SKU | プラン | 初期費用 | 月額 | 上限・条件 |
|---|---|---|---|---|
| **A** | Cloud Light | ¥100,000（自力セットアップなら ¥0） | **¥19,800** | 〜30 名 / 300 文書 |
| **A** | Cloud Standard | ¥100,000 | **¥39,800** | 〜100 名 / 文書無制限 / 監査ログエクスポート |
| **B** | OnPrem | **¥600,000** | **¥60,000** | 名数無制限 / 12 ヶ月契約 / 年 1 回の現地訪問は別途 |
| 共通 | 無料トライアル | ¥0 | ¥0 | 14 日 / 提供元キーで月 300 問まで |

**価格の根拠**:

- **SKU-B 初期 ¥600,000** — 標準化前の実工数は 8 人日相当（ハマリ 13 件の実績）。人日単価 ¥70,000 換算で ¥560,000。
  標準化後は 3 人日（¥210,000）まで下がるため、**改修が進むほど粗利が厚くなる設計**。
- **SKU-B 月額 ¥60,000** — 月 3 時間 × 人時 ¥8,750 = ¥26,250 が原価。粗利率 56%。SLA を平日 9-18 時に限定することが前提（[operations_design.md §8](./operations_design.md)）。
- **SKU-A ¥19,800 / ¥39,800** — 原価は月 1 時間（¥8,750）+ サーバー按分（¥1,000）。粗利率 50%（Light）〜 75%（Standard）。
  ROADMAP の「Standard ¥30,000 / Enterprise ¥100,000」より低く設定した理由は §3.3 に記す。

### 3.2 1 社あたりの損益（月次・定常状態）

| | SKU-A Light | SKU-A Standard | SKU-B |
|---|---|---|---|
| 売上 | ¥19,800 | ¥39,800 | ¥60,000 |
| サーバー按分 | ▲¥1,000 | ▲¥1,500 | ¥0（顧客設備） |
| 運用人件費（内部換算） | ▲¥8,750（1.0h） | ▲¥8,750（1.0h） | ▲¥26,250（3.0h） |
| **粗利** | **¥10,050** | **¥29,550** | **¥33,750** |
| **粗利率** | 51% | 74% | 56% |
| **粗利 / 投入 1 時間** | **¥10,050** | **¥29,550** | **¥11,250** |

> 📌 **最重要の数字は最終行**。1 時間あたりの粗利は **SKU-A Standard が SKU-B の 2.6 倍**。
> 人的リソースが最大の制約であるなら、**中期的に注力すべきは SKU-A Standard**であることが数字から出る。
> ただし SKU-A は「顧客を集める」という別のコスト（マーケティング）が乗るため、短期の現金は SKU-B で作る。

### 3.3 API 実費は顧客にとっていくらか（提案時の説明用）

[api_cost_analysis.md](./api_cost_analysis.md) の実測より、Sonnet 構成で 1 質問あたり約 2〜3 円。

| 規模 | 月の質問数 | 顧客が Anthropic に払う額 | Inquira 月額と合算した総額 |
|---|---|---|---|
| 30 名 | 約 3,300 問 | 約 ¥7,000〜10,000 | Light と合算で 約 ¥27,000〜30,000 |
| 35 名 | 約 7,700 問 | 約 ¥15,000〜25,000 | Standard と合算で 約 ¥55,000〜65,000 |
| 100 名 | 約 22,000 問 | 約 ¥40,000〜70,000 | Standard と合算で 約 ¥80,000〜110,000 |

**価格を ROADMAP の ¥100,000 から下げた理由**: BYO では顧客が API 実費を別途負担するため、
**顧客の体感総額は「月額 + API」**になる。100 名規模で月額 ¥100,000 を取ると総額 ¥17 万となり、
[product_assessment.md](./product_assessment.md) の競合表で優位性の根拠にしていた「ChatGPT Enterprise ¥21 万より安い」という差が薄れる。
**BYO 一本化と ¥10 万の月額は両立しない**。どちらかを選ぶ必要があり、本書は工数削減を優先して BYO ＋ 中価格帯を推奨する。

## 4. 人的リソース制約 = 事業のキャパシティ上限

**本書で最も重要な章。** 収益シミュレーションの前に、そもそも何社まで抱えられるかを確定させる。

### 4.1 工数モデル

| 作業 | SKU-A | SKU-B | 根拠 |
|---|---|---|---|
| 受注前（商談・見積・ヒアリング） | 3 時間 | 8 時間 | ヒアリングシート 6 セクション（[deployment_lessons_learned.md](./deployment_lessons_learned.md)） |
| 初期構築（一括） | 4 時間 | **24〜64 時間** | SKU-B は 3〜8 人日。標準化前は 8 人日、改修後の目標が 3 人日 |
| 定常運用（月あたり） | **1.0 時間** | **3.0 時間** | 外形監視、更新適用、問い合わせ |
| 年次イベント（更新契約・精度レビュー） | 2 時間/年 | 8 時間/年 | |

### 4.2 同時に抱えられる社数

月間可処分時間を **50 時間**（前提 #3 の中央値）とし、その配分を置く。

| 用途 | 配分 | 時間/月 |
|---|---|---|
| 既存顧客の運用 | 50% | 25 時間 |
| 新規導入・営業 | 30% | 15 時間 |
| 製品改修 | 20% | 10 時間 |

**運用 25 時間で抱えられる社数の組み合わせ**:

| 構成 | 運用時間 | 月次 recurring | 判定 |
|---|---|---|---|
| オンプレ 8 社のみ | 24h | ¥480,000 | ⚠ 運用枠が埋まり切る。新規もクラウドも動かせない |
| オンプレ 6 社 + クラウド 7 社 | 25h | ¥360,000 + ¥210,000 = **¥570,000** | ✅ バランス良好 |
| オンプレ 4 社 + クラウド 13 社 | 25h | ¥240,000 + ¥390,000 = **¥630,000** | ✅ 最も効率が良い |
| オンプレ 3 社 + クラウド 16 社 | 25h | ¥180,000 + ¥480,000 = **¥660,000** | ✅ ただしクラウド 16 社の獲得が難所 |

> 📌 **同じ 25 時間でも、オンプレ偏重とクラウド偏重で月商が 18 万円違う。**
> ただしこれは「クラウドの顧客が集まれば」の話であり、集客は工数ではなく認知の問題（§9）。

### 4.3 ここから導かれる 3 つの経営判断

1. **オンプレの同時契約数に上限を設ける（推奨: 6 社、絶対上限 8 社）。**
   9 社目の引き合いが来たら、値上げ（初期 ¥900,000）か待機列か、パートナー経由（§9）に回す。
   「断る」ではなく「価格で調整する」のが正しい対応。
2. **運用工数を下げる改修は、新機能開発より優先度が高い。**
   オンプレ 1 社の月次工数を 3.0h → 1.5h にできれば、それだけで**同時契約可能社数が倍になる**。
   §7 のバックログはこの観点で並べてある。
3. **クラウドの自動化（申込〜プロビジョニング〜課金）に投資しない限り、月商 60 万円台が天井になる。**
   手作業でクラウドを増やすと 1 社あたり 1.0h が下がらず、オンプレと同じ壁にぶつかる。

## 5. 収益シミュレーション（24 ヶ月）

24 ヶ月後の到達点を 3 ケースで置く。月次 recurring と、累計売上（初期費用を含む）を示す。

### 5.1 保守ケース（オンプレ 3 社 / クラウド 5 社）

| | 社数 | 単価 | 月次 |
|---|---|---|---|
| SKU-B | 3 | ¥60,000 | ¥180,000 |
| SKU-A（Light:Standard = 3:2） | 5 | 平均 ¥27,800 | ¥139,000 |
| **合計 recurring** | | | **¥319,000/月** |
| 初期費用（累計） | | | ¥1,800,000 + ¥300,000 = ¥2,100,000 |
| **24 ヶ月累計売上（概算）** | | | **約 ¥490 万**（年商換算 245 万） |

**この水準の意味**: 副業・一人事業としては成立するが、専任者を雇う原資にはならない。

### 5.2 標準ケース（オンプレ 6 社 / クラウド 12 社）★ 本命

| | 社数 | 単価 | 月次 |
|---|---|---|---|
| SKU-B | 6 | ¥60,000 | ¥360,000 |
| SKU-A（Light:Standard = 1:1） | 12 | 平均 ¥29,800 | ¥357,600 |
| **合計 recurring** | | | **¥717,600/月** |
| 初期費用（累計） | | | ¥3,600,000 + ¥600,000 = ¥4,200,000 |
| **24 ヶ月累計売上（概算）** | | | **約 ¥1,110 万**（年商換算 555 万） |

**この水準の意味**: 24 ヶ月目の月商 71 万は、**1 人目の運用担当（パート・業務委託）を雇える水準**。
雇えれば §4 のキャパシティ上限が外れ、その先の成長曲線に乗る。**本計画の目標はここ**。

### 5.3 強気ケース（オンプレ 8 社 / クラウド 25 社）

| | 社数 | 単価 | 月次 |
|---|---|---|---|
| SKU-B | 8 | ¥60,000 | ¥480,000 |
| SKU-A | 25 | 平均 ¥32,000 | ¥800,000 |
| **合計 recurring** | | | **¥1,280,000/月** |

**達成条件**: クラウドの申込〜課金が完全自動化されており（§7 の C 群完了）、
かつオンプレ運用の一部をパートナーに委譲できていること。**片方でも欠けると §4.2 の壁で頭打ちになる。**

### 5.4 判定 — 収益は見込めるか

| 問い | 答え |
|---|---|
| 単体で黒字になるか | **YES**。両 SKU とも粗利率 50% を超え、変動費はほぼゼロ（BYO のため） |
| 現在の人的リソースで回るか | **YES、ただし同時 6〜8 社まで**。それ以上は自動化かパートナーが前提 |
| ROADMAP の「月商 100 万」に届くか | **24 ヶ月では標準ケースで 72 万。100 万は 30〜36 ヶ月の目標に置き直すべき** |
| 最大のリスクは何か | 技術ではなく **集客**。プロダクトは v0.8.0 で本番実績があり、作り込みは足りている |

> **結論**: 収益は見込める。ただし ROADMAP が掲げる「Enterprise ¥10 万 × 10 社 = 月 100 万」は
> **BYO 一本化・低リソース前提と整合しない**ため、本書の標準ケース（月 72 万）に目標を置き換えることを推奨する。

## 6. 現状プロダクトのギャップ

v0.8.0 で「売れる状態」にどれだけ近いかの棚卸し。

| 領域 | 現状 | 2 SKU 販売への影響 |
|---|---|---|
| コア機能（RAG・出典・確信度・マスキング・監査ログ） | ✅ 実装済・本番実績あり | 問題なし |
| トークン使用量の記録 | ✅ `app/llm.py` が `llm_usage` を監査ログに記録済 | レポート自動化の土台は既にある |
| 管理画面の利用状況集計 | ✅ `app/main.py` でトークン・コスト集計済 | 顧客への月次報告に流用可 |
| **API キーの顧客自己設定** | ❌ `.env` 直編集のみ（`runtime_settings.py` が機密キーを意図的に除外） | **BYO の致命的ボトルネック**。キー更新のたび提供元が SSH する羽目になる |
| **使用量クォータ / レート制限** | ❌ 未実装（[billing_design.md §4](./billing_design.md) で「将来実装」） | トライアル提供と顧客の課金事故防止ができない |
| **決済** | ❌ 未実装 | クラウドを人手なしで売れない |
| **契約管理（有効期限・停止）** | ❌ 未実装 | 未払い時に手作業で止めることになる |
| **プロビジョニング自動化** | ❌ 手順書のみ（`deploy/multi-tenant/README.md` に「将来 `provision-client.sh`」と記載） | クラウド 1 社あたりの工数が下がらない |
| インストーラ | 🟡 `install.ps1` / `install.sh` はあるが OS 判定・事前チェックが不十分 | オンプレ導入工数（= 粗利）に直結 |
| 法務文書 | 🟡 利用規約・プライバシーポリシー・特商法表記の**雛形は揃っている**（`docs/legal/`） | 実在情報への差し替えと士業レビューが未了 |
| 精度（検索バックエンド） | 🟡 既定は TF-IDF。e5 系に切替可能だが未検証 | 「該当情報なし」の多発は問い合わせ工数を増やす |

## 7. 製品改修バックログ（ROI 順）

**並べ替えの基準は「新機能かどうか」ではなく「1 時間の実装が、将来どれだけの運用時間を消すか」。**

### A 群 — 売る前に必須（Month 1〜2 / 計 12 人日）

| # | 項目 | 工数 | 効果 |
|---|---|---|---|
| **A-1** | **API キーを管理画面から設定・疎通テストできるようにする** | 2 日 | BYO の前提条件。キー更新のたびの SSH 対応（1 回 30 分 × 全社）が消える。`runtime_settings.py` の除外方針を変更し、**保存先を暗号化 + 画面ではマスク表示**する形で安全に開放する |

## 8. 展開計画

```
Month 1-2   ┃ A群 (売れる状態を作る)          ┃ 受注: 0        ┃ 月商: 既存のみ
Month 3-6   ┃ B群 + オンプレ集中営業           ┃ オンプレ +2社  ┃ 月商 12-18万
Month 7-12  ┃ C-1,C-3 + クラウドβ(招待制)     ┃ +オンプレ2/クラウド4 ┃ 月商 35-40万
Month 13-18 ┃ C-2,C-4 + クラウド一般公開       ┃ +クラウド5社   ┃ 月商 55-60万
Month 19-24 ┃ パートナー経由の拡販 + D群       ┃ +クラウド3/オンプレ2 ┃ 月商 70-75万
```

### Phase 0（Month 1〜2）— 売れる状態を作る

- **やること**: A 群（A-1〜A-6）を完遂する。価格を確定し、契約書・見積書の雛形を作る。
- **やらないこと**: 新機能の追加。この 2 ヶ月は 1 件も新機能を入れない。
- **完了条件**: 「契約書を出せば、その日から課金を開始できる」状態。
- **リスク**: 法務レビューの外注待ちで止まる → A-4 を最初に着手し、レビュー中に A-1〜A-3 を並行実装する。

### Phase 1（Month 3〜6）— オンプレで現金を作る

- **やること**: B 群と並行してオンプレ 2 社の受注を狙う。第 1 号顧客の稼働実績を事例化して営業資材にする。
- **なぜオンプレ優先か**: 初期費 ¥600,000 が即座の現金になり、C 群（クラウド自動化 23 人日）の投資原資になるため。
  **クラウドを先に作ると、収入がない期間が 12 ヶ月続く。**
- **完了条件**: オンプレ 3 社稼働・導入工数が 5 人日以内に収まっていること。
- **注意**: この期間に**オンプレを 4 社以上受注しない**。運用工数が Phase 2 の開発時間を食い潰す。

### Phase 2（Month 7〜12）— クラウドを招待制で立ち上げる

- **やること**: C-1（プロビジョニング自動化）と C-3（オンボーディングウィザード）を先に作り、**課金は手動請求のまま**でクラウド β を 4 社。
- **なぜ Stripe を後回しか**: 4 社なら請求書を手で出しても月 30 分。**顧客が付くか分からない段階で 8 人日を決済に使うのは順序が逆**。
- **完了条件**: クラウド 4 社が稼働し、1 社あたり月次工数が 1 時間以内に収まっていること。
- **判断ポイント**: ここでクラウドが 4 社埋まらなければ、C-2 に進まず **オンプレ特化に戦略を切り替える**（§10 の撤退基準）。

### Phase 3（Month 13〜18）— クラウドを一般公開する

- **やること**: C-2（Stripe）と C-4（運営コンソール）を実装し、申込〜利用開始を無人化。オウンドメディアでの集客を開始。
- **完了条件**: 提供元が一度も対応せずに 1 社が契約・稼働に至ること（＝真の自動化の証明）。

### Phase 4（Month 19〜24）— レバレッジをかける

- **やること**: §9 のパートナー展開。D 群で継続率を上げる。
- **判断ポイント**: 月商 70 万を超えた時点で、**運用担当の業務委託採用を検討**する。§4 のキャパシティ上限を外す唯一の手段。

## 9. 販売チャネル — 人手をかけずに顧客を見つける

集客が最大のボトルネックであり、かつ最も工数を食う。**訪問営業は選択肢から外す**（1 社あたり 8 時間の商談は §4 の予算に収まらない）。

| チャネル | 想定 SKU | 工数 | 評価 |
|---|---|---|---|
| **既存顧客からの紹介** | B | 極小 | ⭐ 最優先。第 1 号顧客の稼働実績が最強の営業資材 |
| **オウンドメディア（技術記事）** | A | 記事 1 本 4 時間 | ⭐ 既に `docs/blog_post*.md` の資産がある。「オンプレ社内 AI 導入の失敗記録」は刺さる層が明確 |
| **地場 SIer・情シス代行業者とのパートナー契約** | B | 初期 8 時間 / 社 | ⭐ **人的リソース制約の唯一の突破口**。導入作業を委譲し、レベニューシェア 30%。月額 ¥60,000 のうち ¥18,000 を渡しても、自分の 3 時間/月が空く方が価値が高い |
| **「NotebookLM を試したが全社展開で詰まった」層への提案** | A/B | 記事 + 提案テンプレ | ⭐ [competitive_positioning.md](./competitive_positioning.md) で整理済のポジション。刺さる層が最も明確 |
| 広告出稿 | A | 金銭コスト | 🔺 認知ゼロの段階では CPA が読めない。Phase 3 以降に少額でテスト |
| 訪問営業 | B | 8 時間/社 | ❌ 工数が合わない |

## 10. KPI と撤退基準

### 10.1 追う指標（月次で見る 5 つだけ）

| KPI | 目標 | 意味 |
|---|---|---|
| MRR（月次経常収益） | Month 12 で ¥350,000 / Month 24 で ¥700,000 | 事業の本体 |
| **1 社あたり月次運用時間** | オンプレ 2.0h 以下 / クラウド 1.0h 以下 | **これが守れないと社数を増やせない**。最重要 |
| 導入所要工数（オンプレ） | 5 人日以内、最終目標 3 人日 | 初期費 ¥600,000 の粗利を決める |
| 解約率 | 年 10% 以下 | BYO はキー切れで簡単に止まるため要監視 |
| 「該当情報なし」率 | 20% 以下 | 解約の先行指標。管理画面で計測済 |

### 10.2 撤退・方針転換の基準

| 時点 | 条件 | 取るべき行動 |
|---|---|---|
| Month 6 | オンプレの有料契約が 2 社に届かない | 価格が高すぎるか、対象業界が違う。**値下げではなくターゲット業界の見直し**（規制業界への集中） |
| Month 12 | クラウド β が 4 社に届かない | **C-2（Stripe・8 人日）に進まない**。クラウドを畳み、オンプレ受託 + パートナー展開に一本化する |
| Month 12 | 1 社あたり運用時間が目標の 2 倍を超えている | 新規受注を止め、B 群・C 群の自動化を完遂するまで営業を停止する |
| 随時 | Anthropic が同等機能を直接提供し始めた | 差別化軸を「オンプレ・データ主権・導入代行」に全振りし、ソフトウェア販売から**構築サービス業**へ転換する |

## 11. リスク

| リスク | 影響 | 対策 |
|---|---|---|
| **バス係数 1**（担当者が 1 人） | 商談で必ず突かれる。障害時に復旧できない | SLA を平日 9-18 時に明示的に限定（[operations_design.md §8](./operations_design.md)）。オンプレはデータが顧客側にあるため、**最悪でも顧客のデータは失われない**構造を説明材料にする。ソースコードのエスクロー預託も検討 |
| **BYO キーの停止**（顧客の Anthropic 契約が切れる・与信で止まる） | サービスが即停止し、提供元の障害と誤認される | A-6 のセルフ診断でキー有効性を常時チェックし、失効前に管理者へ通知する |
| **顧客の API 課金事故**（想定外の大量質問） | 「Inquira のせいで高額請求が来た」というクレーム | A-2 のクォータを既定で有効化し、Anthropic Console 側の予算アラート設定を導入チェックリストの必須項目にする |
| **オンプレの過剰受注** | 運用で手が埋まり、成長が完全に止まる | §4.3 の上限を運用ルールとして明文化。9 社目は値上げかパートナー経由 |
| **価格の下振れ圧力** | 粗利率が崩れる | 値下げではなく**プラン下位（Light）への誘導**で対応。オンプレの初期費は絶対に値引きしない（工数が実在するため） |
| **法務未整備のまま販売開始** | 特商法違反・規約不備によるトラブル | A-4 を Phase 0 の最初に着手。雛形は揃っているため差し替えとレビューのみ |
| **精度不足による解約** | LTV が伸びない | D-1 の検証を Phase 2 までに実施。「該当情報なし」率を KPI として監視 |

## 12. 次アクション（着手順）

1. **価格の確定** — §3.1 の推奨値を承認するか修正する。ここが決まらないと他が全て止まる。
